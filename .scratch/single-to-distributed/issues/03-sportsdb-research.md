# The Sports DB API 조사

Type: research
Status: resolved

## Question

The Sports DB API로 스포츠 경기 콘텐츠를 수집하려 할 때 알아야 할 사실을 공식 문서에서 확인한다.

- **키 발급** — 무료 티어의 발급 방법과 제약. 공개 테스트 키의 한계, 유료 티어와의 차이.
- **경기(이벤트) 목록 엔드포인트** — 조회 축이 무엇인가(리그별/날짜별/시즌별). 전체를 훑는 것이 가능한가, 아니면 축을 정해 좁혀야 하는가.
- **증분 수집 가능 여부**와 rate limit.
- **스키마 대응** — 응답 필드를 프론트 계약(`api.json`)의 콘텐츠 스키마에 어떻게 대응시킬지. 영화·드라마와 필드 성격이 다를 텐데 **하나의 콘텐츠 모델로 합칠 수 있는지**가 도메인 모델 결정에 직접 영향을 준다.
- **데이터 안정성** — 필드 누락이나 타입 불일치가 흔한지. 흔하다면 수집 시 방어가 필요하다.

출처는 The Sports DB 공식 문서를 1차로 삼는다.

## Answer

전문은 [`research/sportsdb-api.md`](../research/sportsdb-api.md) (약 410줄). 문서가 얇고 **일부는 실제와 다르다**는 것이 확인되어, 무료 키 `123`으로 약 120회 실측한 뒤 모든 주장에 **[문서]** / **[실측]**(2026-09-02) 표기를 붙였다. 표본: `eventsday` 25일치 90경기 + `eventsseason` 전량.

### 통합 콘텐츠 모델에 대한 판정

**이미 프론트 계약이 정해놓았다 — 그게 이 조사의 답이다.** `api.json`의 `ContentDto`는 `type: movie | tvSeries | sport`를 **required enum**으로 갖고, `GET /api/contents`가 `typeEqual`로 셋을 함께 필터한다. 단일 `Content` 모델은 선택지가 아니라 제약이다.

진짜 질문은 **그 안에서 무엇이 깨지는가**다.

| 계약 필드 | 소스 | 실측 |
| --- | --- | --- |
| `title` | `strEvent` | 90/90 — 문제없음 |
| `thumbnailUrl` | `strThumb` | **79/90 (88%)** — `strLeagueBadge` 폴백 필요(90/90) |
| `description` | `strDescriptionEN` | **90개 중 1개** |

- `description`은 `ContentDto`에서 **required**인데 사실상 비어 온다. **우리가 합성해야 한다.** 게다가 `eventsseason.php`와 v2 시즌 스케줄은 이 필드를 **아예 반환하지 않으므로**, 대량 수집 경로에서는 원본을 얻을 방법이 없다.
- **`ContentDto`에 날짜 필드가 하나도 없다.** `releaseDate`도 `startsAt`도 없고, 정렬 축은 `createdAt | watcherCount | rate`뿐이다. 경기 시작 시각(`strTimestamp`, 90/90)을 놓을 자리가 없고 **"다가오는 경기" 정렬이 불가능하다.** 개봉일 없는 영화는 목록에 그냥 뜨지만, 시작 시각 없는 경기 목록은 의미가 없다.
- 경기는 **생성 후 변한다** — 90건 중 46건이 점수 null(미래 경기)이고, `strStatus`로 취소(`NS`/`FT`/`CANC`)된다. 영화에는 없는 개념이다.
- 90건 중 5건은 **홈/원정 팀이 null**(육상·배드민턴). 스포츠끼리도 균질하지 않다.

권고: 계약대로 `Content`는 단일로 두되, 스포츠 고유 속성(`strTimestamp`, 팀, 점수, `strStatus`, 리그, 시즌)은 **부속 테이블로 분리**한다. 계약에 자리가 없다고 버리면 sport 타입 자체가 껍데기가 된다.

### 그 외 무게를 지는 발견

- **무료 키로는 배치가 불가능하다.** 문서의 상한이 곧 결과 배열 길이임을 실측 확인: `all_leagues` → 10개(전부 유럽 축구), `eventsday` → **전 세계 통틀어 하루 3경기**, `eventsseason` → 380경기 시즌 중 15개. **리그 목록조차 열거할 수 없다.** 실질 최소선은 **$9/월**.
- **Patreon은 더 이상 접근 경로가 아니다** — `/pricing` 478행에서 Patreon 링크가 HTML 주석 처리되어 있고, 결제는 PayPal/카드 직접이다. $9/월, $90/년, $295 평생 / Business $20·$200·$999.
- **증분 수집이 존재하지 않는다.** changed-since 엔드포인트도, 이벤트의 `dateUpdated` 필드도 없다. 유일한 `updated`는 프리미엄 라이브스코어 피드 **안의 스냅샷**이지 질의 필터가 아니다. `idEvent` + unique 제약 + upsert가 유일한 중복 제거 경로다.
- **429가 JSON이 아니다.** Cloudflare가 `content-type: text/plain`, 본문 `error code: 1015`, `Retry-After: 119`로 응답한다. 순진한 역직렬화기는 이걸 **rate limit이 아니라 "깨진 JSON"으로 실패**시킨다. 게다가 스로틀은 문서의 30/분이 아니라 **43번째 요청**에서 걸렸다 — 무료 키는 공유 버킷이라 문서 숫자를 믿을 수 없다.
- **같은 엔티티인데 엔드포인트마다 필드 수가 다르다**: `eventsday` 49개, `eventsseason` 30개, v2 시즌 스케줄 20개(380건 전량 확인). **DTO의 모든 필드가 nullable이어야 한다.**
- 숫자가 전부 JSON **문자열**로 온다. "없음"이 같은 필드에서 `null`과 `""`로 섞인다. `intRound`가 실제 라운드 번호와 코드(200=결승, 500=프리시즌)를 겸한다. `strSeason` 형식이 리그마다 다르다(`2024-2025` vs `2026`) — **추측하지 말고 조회해야 한다.** `strTimeLocal`은 일부 레코드에서 명백히 틀렸다 — `strTimestamp`만 믿는다.
- **한국어가 전혀 없다.** 이벤트는 `strDescriptionEN`뿐이고, 리그는 15개 언어 변형이 있으나 한국어는 없다. 로케일 파라미터 자체가 없다. TMDB와 대조적이다.

### 확인하지 못한 것 (전문 7장, 8건)

프리미엄 동작은 **전혀 검증되지 않았다** — 무료 티어에서 이미 문서 숫자가 틀린 것이 드러났으므로 **구매 후 재측정해야 한다.** v2는 키 없이 HTTP 400이라 실호출을 못 했고, 상한 초과 시 페이지네이션 거동은 문서에 없으며, 문서 개정일이 공표되지 않는다.
