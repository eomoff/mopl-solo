# 분산 전환 이음매 확정

Type: grilling
Status: resolved
Blocked by: 01

## Question

**무엇을 인터페이스 뒤에 숨기고 시작할 것인가.**

"단일로 만들고 나중에 분산으로 넘어간다"는 계획은 넘어갈 지점을 미리 정해두지 않으면 실패한다. 단일 인스턴스에서는 그냥 메모리에 두면 되지만 인스턴스가 늘어나는 순간 깨지는 상태를 식별하고, 각각에 대해 셋 중 하나를 고른다.

- **(ㄱ)** 처음부터 분산 구현으로 간다
- **(ㄴ)** 인터페이스 뒤에 단일 구현을 두고 나중에 갈아끼운다
- **(ㄷ)** 그냥 단일 구현으로 두고 전환 때 다시 짠다

후보:

- **실시간 시청 세션** — 누가 어떤 콘텐츠를 보고 있는가, 시청자 수
- **SSE 연결 레지스트리** — 알림을 보내려면 그 사용자의 연결이 어느 인스턴스에 붙어 있는지 알아야 한다
- **WebSocket 세션과 메시지 브로커** — 콘텐츠 채팅·DM을 같은 방의 다른 인스턴스 사용자에게 전달
- **이벤트 발행** — 단일에선 `ApplicationEventPublisher`, 분산에선 Kafka
- **캐시**
- **인증 세션 무효화** — 강제 로그아웃·계정 잠금이 즉시 반영되어야 하는데 JWT는 스스로 무효화되지 않는다
- **업로드된 프로필 이미지** — 로컬 디스크는 인스턴스가 늘면 깨진다
- **배치 실행** — 인스턴스가 2대면 배치도 2번 돈다

각 항목에 **"이 결정을 나중에 되돌리는 비용"** 을 함께 기록한다. 되돌리기 싼 것은 (ㄷ)이어도 된다. 이음매를 전부 (ㄱ)이나 (ㄴ)으로 덮으면 단일 인스턴스 단계가 사라지고, 그러면 이번 연습의 주제 자체가 없어진다.

이 지도의 중심 티켓이다. 인증·실시간·알림·마일스톤이 모두 여기에 매인다.

## Answer

### 결정

| # | 이음매 | 결정 | 되돌리는 비용 |
| --- | --- | --- | --- |
| 1 | 시청 세션 상태 | **(ㄱ) 처음부터 Redis** | — (전환 없음) |
| 2 | WebSocket 브로커 | **(ㄴ) simple broker + 발행 지점 인터페이스** | 낮음 (브로커 릴레이는 설정 교체에 가깝다) |
| 3 | SSE 연결 레지스트리 | 인메모리 + 알림은 DB. **Q2와 하나의 이음매로 통합** | 낮음 (Q2와 함께 해결) |
| 4 | 이벤트 발행 | **(ㄴ) 인터페이스 뒤** | **높음** — 발행 지점이 도메인 전역에 흩어진다 |
| 5 | JWT 무효화 | 짧은 액세스 토큰 + DB 무효화 마커 | 낮음 |
| 6 | 업로드 파일 | (ㄴ) 인터페이스 뒤 로컬 디스크 → S3 | 낮음 (2메서드 인터페이스) |
| 7 | 배치 중복 실행 | (ㄷ) 전환 시점에 잠금 추가 | 가장 낮음 |
| 8 | 캐시 | (ㄴ) Spring Cache 추상화 | 가장 낮음 (설정 수준) |

### 계약이 이 결정에 건 제약

- **`ContentDto.watcherCount`가 required** — 콘텐츠 목록 조회마다 항목별 현재 시청자 수가 필요하다. 상태가 인스턴스마다 흩어지면 목록 조회 자체가 틀린 값을 낸다.
- **`GET /api/users/{watcherId}/watching-sessions`가 단건 반환** — **한 사용자는 최대 하나의 시청 세션**. 도메인 규칙이 계약에 박혀 있다.
- **`GET /api/sse`가 `LastEventId` 쿼리 파라미터를 받는다** — 재연결 시 놓친 알림 재전송이 요구사항이다.

### Q1이 (ㄱ)으로 간 결과 — 이 결정의 파급

**Redis가 1일차 의존성이 된다.** `docker-compose`에 처음부터 Redis가 있어야 하고, 로컬 개발과 테스트(Testcontainers)가 그 전제 위에서 돌아간다. 이 파급 때문에 새 티켓 [로컬 개발·분산 환경 구성]을 만들었다.

**시청 세션에서는 전환을 겪지 않는다.** 처음부터 분산 가능한 형태이므로, 인스턴스를 2대로 늘려도 시청자 수와 시청자 목록은 그대로 맞는다. 이 노력의 학습 대상에서 이 항목 하나가 빠지는 것을 감수한 선택이다. **전환 체험은 Q2(브로커)에 집중된다** — 거기서 채팅이 반쪽만 보이는 것을 직접 보게 된다.

**Q5·Q8의 결정은 유지되지만 근거 하나가 무효가 됐다.** 두 항목을 추천할 때 "Redis 없이 시작할 수 있다"를 근거로 들었는데, Redis가 1일차에 존재하므로 그 근거는 사라졌다. 결정 자체는 각자의 이유로 여전히 유효하다.

- **Q5** — `locked`·`role`은 어차피 DB가 소스 오브 트루스다. Redis가 있다고 해서 토큰 블랙리스트를 Redis에 둘 이유가 생기지는 않는다. 단, 매 요청 DB 조회가 부담이 되면 **Redis 캐시를 얹는 선택지가 이제 즉시 가능**하다(Q8과 합류).
- **Q8** — 추상화 뒤에 둔다는 결정은 그대로다. 다만 단일 단계에서도 **로컬 캐시 대신 Redis를 바로 쓸 수 있다.** 어느 쪽으로 갈지는 캐시 대상이 정해질 때 함께 정한다(안개 항목).

### Q2 + Q3 = 하나의 이음매

둘은 따로 풀 문제가 아니다. 실체는 **"다른 인스턴스에 붙은 사용자에게 어떻게 전파하는가"** 하나이고, 콘텐츠 채팅·시청 세션 JOIN/LEAVE·SSE 알림이 모두 같은 문제의 다른 얼굴이다. 따라서 **전환 작업도 하나**다 — pub/sub 경로를 한 번 만들면 셋이 함께 해결된다.

`LastEventId` 재전송은 이 이음매 밖이다. DB 조회이므로 연결이 어느 인스턴스에 붙었든 무관하다.

### 인터페이스는 계약이 규정한다 (Q1의 함정 회피)

Q1이 (ㄱ)으로 갔으므로 Redis 구현이 곧 유일한 구현이지만, **인터페이스의 모양은 여전히 계약이 정한다.** 시청 세션 저장소는 다음 세 질의를 제공해야 한다.

1. **콘텐츠 여러 개의 시청자 수를 한 번에** — 목록 조회에서 N+1이 나지 않아야 한다
2. **콘텐츠별 시청자 목록** — 이름 부분 검색 + 커서 페이지네이션 + 총개수
3. **사용자별 단건 조회**

특히 ②의 이름 검색은 Redis 자료구조 선택을 직접 구속한다. 단순 `SET`으로는 안 된다.

### 의도를 남기는 방법 (Q2 단서)

Q2의 simple broker는 **고장이 아니라 의도된 미완성**이다. 이 사실이 코드만 봐서는 드러나지 않으므로 세 곳에 남긴다.

1. **이 티켓** — git으로 추적되므로 결정과 근거가 저장소 안에 남는다.
2. **발행 인터페이스의 문서 주석** — "단일 인스턴스 전용 구현. 인스턴스가 2대 이상이면 다른 인스턴스의 구독자에게 전달되지 않는다. 전환 시 브로커 릴레이로 교체한다"를 구현체가 아니라 **인터페이스에** 적는다.
3. **전환을 검증하는 테스트** — 새 티켓 [이음매를 감싸는 테스트 전략]에서 다룬다. 인스턴스 2대에서 깨지는 것을 **드러내는** 테스트가 있어야 전환이 끝났는지 알 수 있다.

### 남은 위험

이 결정들의 조합은 단일 인스턴스 단계에서 **인터페이스는 많고 구현은 사소한** 상태를 만든다. 갈아끼울 계획이 실재하므로 과설계가 아니지만, **계획이 실행되지 않으면 그때는 과설계가 된다.** [12주 마일스톤 구획]에서 전환 시점을 실제 일정에 박아야 이 결정들이 값을 한다.


## 수정 (2026-09-03, [도메인 모델 확정] 해결 중)

**1번 이음매의 결정이 수정됐다.** 이 티켓을 풀 때 놓친 사실이 [도메인 모델 확정]에서 드러났다.

`GET /api/contents`의 `sortBy`에 **`watcherCount`가 포함된다** — 커서 페이지네이션·`totalCount`와 함께. Redis에 있는 값으로는 DB 테이블을 정렬하고 페이지를 끊을 수 없다. 이 티켓을 풀 때는 `watcherCount`가 `ContentDto`에 required라는 것까지만 확인했고, **정렬 축이기도 하다는 것**은 목록 엔드포인트의 질의 파라미터를 열어본 뒤에야 드러났다.

**수정된 결정**: 시청 세션 상태는 여전히 Redis에 두되, **집계값(`watcher_count`)은 `contents` 테이블에 비정규화 컬럼으로 함께 유지한다.**

즉 Redis의 역할이 바뀐다.

| | 수정 전 | 수정 후 |
| --- | --- | --- |
| Redis | 시청 세션의 소스 오브 트루스 | **실시간 세션 레지스트리** (누가 무엇을 보고 있는가, 시청자 목록 조회) |
| DB | 관여 없음 | **집계값** `contents.watcher_count` (정렬·필터·목록 응답용) |

**새로 생긴 대가**: 같은 값이 두 곳에 있다. 연결 비정상 종료나 Redis 재시작으로 어긋날 수 있으므로 **주기적 재계산이 필요하다** → [콘텐츠 수집 배치 설계].

**변하지 않은 것**: 나머지 7개 이음매의 결정, 그리고 "전환 체험은 브로커에 집중된다"는 구도.

이 수정은 이 티켓을 풀 때 계약을 충분히 파고들지 않아 생겼다. 남은 이음매 판단에도 같은 함정이 있을 수 있으므로, **목록 엔드포인트의 정렬·필터 파라미터는 관련 티켓마다 먼저 확인한다.**
