# 인증·인가와 토큰 무효화 설계

Type: grilling
Status: resolved
Blocked by: 01, 04

## Question

인증·인가를 설계한다. 계약이 고정한 부분과 분산 환경에서 깨지는 부분을 나눈다.

- **JWT 액세스/리프레시 구조** — 만료 시간, 리프레시 토큰 저장 위치, 회전 여부.
- **CSRF** — `info.md`가 쿠키(`XSRF-TOKEN`)/헤더(`X-XSRF-TOKEN`) 방식을 지정했다. JWT를 헤더로 보내는데 CSRF가 왜 필요한지부터 정리하고, Spring Security 설정을 어떻게 할지 정한다.
- **강제 로그아웃과 계정 잠금** — 권한 변경·계정 잠금 시 즉시 로그아웃되어야 한다. JWT는 스스로 무효화되지 않으므로 블랙리스트나 짧은 만료가 필요하다. **분산 전환 이음매의 결정에 직접 매인다.**
- **동시 로그인** — `info.md`는 "기존 로그인 강제 로그아웃"을 요구하면서, 프로토타입은 데모 편의를 위해 동시 로그인을 허용한다고 단서를 단다. 어느 쪽을 구현할 것인가.
- **소셜 로그인** — Google/Kakao. 카카오는 이메일을 못 주므로 `{닉네임}_{회원ID}@kakao.com` 가상 이메일을 쓴다. 기존 계정과의 연결 규칙은 무엇인가. 실패 시 리다이렉트 계약(`error`, `error_message` 쿼리 파라미터)을 어떻게 만족시킬 것인가.
- **임시 비밀번호** — 3분 만료를 어디에 저장할 것인가. 이것도 이음매 후보다.

---

**[분산 전환 이음매 확정]이 이 티켓에 넘긴 것**

- **무효화는 짧은 액세스 토큰 + DB 마커로 간다.** `locked`·`role`은 어차피 DB가 소스 오브 트루스다. Redis가 1일차에 존재하지만, 그것만으로 블랙리스트를 Redis에 둘 이유는 생기지 않는다. 매 요청 DB 조회가 부담이면 캐시를 얹는다(캐시 대상은 아직 안개).
- **정적 리소스를 `permitAll`로 열어야 한다** — 프론트엔드가 `src/main/resources/static/`에서 같은 오리진으로 서빙된다.
- **계약이 넘긴 사실** — `POST /api/auth/sign-in`이 `application/x-www-form-urlencoded`다(JSON이 아니다). 소셜 로그인 경로는 OpenAPI에 없고 `vite.config.ts`만 `/oauth2` 프록시를 언급한다. 어드민 전용 경로가 없어 **인가가 경로가 아니라 메서드 수준**에서 갈린다.


**[도메인 모델 확정]이 이 티켓에 넘긴 것**

- **`auth` 패키지는 엔티티 없이 시작한다.** 계약상 인증이 소유한 고유 엔티티가 보이지 않는다. **이 티켓이 리프레시 토큰과 임시 비밀번호를 어디에 둘지 정하면서 `auth`에 저장할 것이 실제로 생기는지 판정한다.**
- **사용자 탈퇴 경로가 계약에 없다** (`DELETE /api/users/{userId}` 부재). 탈퇴를 구현할 것인가? 구현하지 않으면 "탈퇴한 사용자의 리뷰·플레이리스트를 어떻게 하는가"라는 문제가 통째로 사라진다. **잠긴 계정(`locked`)은 삭제와 다른 상태**라는 점도 함께 정리한다.


**[실시간 WebSocket 아키텍처 설계]가 넘긴 것**

- **WebSocket 인증은 STOMP `CONNECT` 프레임의 `Authorization` 헤더**에서 이뤄진다(HTTP 핸드셰이크가 아니다). SSE도 같은 헤더 방식이다.
- **연결 도중 토큰이 만료돼도 연결은 유지한다.** 대신 **강제 로그아웃·계정 잠금 시 서버가 그 사용자의 WS 세션을 직접 끊어야 한다** — 무효화 마커를 세우는 바로 그 지점에서 함께 처리한다. 이 티켓이 그 연결 지점을 설계한다.


## Answer

> **결정 주체**: Q1·Q2는 사용자 선택. Q3~Q7은 에이전트가 추천하고 사용자가 승인했다.

### 프론트엔드 코드가 이미 답한 것

| 항목 | 사실 | 근거 |
| --- | --- | --- |
| 액세스 토큰 저장 | **메모리에만** (persist 없음) | `useAuthStore` |
| 복구 경로 | `ProtectedRoute` 마운트 시 `POST /api/auth/refresh` | "새로고침 시 refresh token을 사용하여 인증 상태 복구" |
| 재발급 트리거 | **401** (403 아님), `/auth/` 제외, 1회만 재시도 | `client.ts` 응답 인터셉터 |
| refresh 인증 | Authorization 헤더를 **의도적으로 제외**, 쿠키만 | `!config.url?.includes('/auth/refresh')` |
| CSRF | `XSRF-TOKEN` 쿠키를 JS가 읽어 `X-XSRF-TOKEN` 헤더로 | `document.cookie.match(...)` |
| 로그인 | `x-www-form-urlencoded`, 필드명 `username`(값은 이메일) | `URLSearchParams` |
| OAuth | `/oauth2/authorization/{google\|kakao}` (Spring Security 기본 경로) | `SignInForm.tsx` |

**따라오는 구현 제약 셋**

- **`REFRESH_TOKEN` 쿠키는 브라우저 재시작을 견뎌야 한다.** 액세스 토큰이 메모리에만 있으므로 세션 쿠키로 만들면 껐다 켤 때마다 재로그인이 된다.
- **`XSRF-TOKEN` 쿠키는 `HttpOnly`가 아니어야 한다** — JS가 읽는다. `CookieCsrfTokenRepository.withHttpOnlyFalse()`.
- **OAuth 성공 시 URL에 토큰을 실을 필요가 없다.** 리프레시 쿠키만 심고 SPA로 리다이렉트하면 `ProtectedRoute`가 복구한다.

### Q1. 리프레시 토큰을 저장한다 — **(a), 사용자 선택 (에이전트 추천과 일치)**

DB 테이블에 저장하고 **매 refresh마다 회전**한다(새로 발급, 이전 것 폐기). 이전 토큰이 재사용되면 탈취로 보고 해당 사용자의 토큰을 전부 무효화한다.

만료: **액세스 15분 / 리프레시 14일.**

무상태(서명만 검증) 방식을 버린 이유: 발급한 토큰을 서버가 되돌릴 방법이 없어 **`info.md`의 "권한 변경 시 자동 로그아웃"을 만족시킬 수 없다.**

**이 결정이 [도메인 모델 확정]의 미뤄둔 질문에 답한다** — `auth` 패키지에 저장할 것이 실제로 생겼다. **리프레시 토큰**과 Q5의 **소셜 계정 연결** 둘이다.

### Q2. 동시 로그인을 막는다 — **사용자 선택 (에이전트 추천과 일치)**

`info.md` 본문의 "기존에 로그인된 계정이 있을 경우 강제로 로그아웃"을 따른다. 바로 아래 참고("프로토타입에서는 데모 편의를 위해 동시 로그인 허용")는 **프로토타입 서버의 편의**일 뿐 요구사항이 아니라고 판단했다.

Q1에서 리프레시 토큰을 저장하므로 **"사용자당 유효 리프레시 토큰 1개"로 거의 공짜로 구현된다.**

**분산 환경에서 이 결정이 커진다** — 아래 참조.

### Q3. 즉시 반영은 Redis 무효화 목록 — **에이전트 추천 / 사용자 승인**

액세스 토큰이 15분이면 최대 15분 지연되는데 요구사항은 즉시다. **잠기거나 권한이 바뀐 사용자만 Redis 목록에 넣고 TTL을 액세스 토큰 수명(15분)으로 잡는다.** TTL이 지나면 어차피 토큰이 만료되므로 자동 정리된다. 인증 필터가 매 요청 조회 1회를 하지만 대부분의 사용자는 목록에 없다.

**이는 [분산 전환 이음매 확정]의 "짧은 액세스 토큰 + DB 무효화 마커"를 구체화하면서 한 단계 옮긴 것이다.** 그 티켓이 "매 요청 DB 조회가 부담되면 캐시를 얹는다"고 단서를 달아뒀고 여기가 그 지점이다. **`locked`·`role`의 소스 오브 트루스는 여전히 DB다.**

권한이 바뀌는 순간 **세 가지를 함께** 한다:

1. Redis 무효화 목록에 등록
2. 리프레시 토큰 폐기
3. **WebSocket 세션 종료** ([실시간 WebSocket 아키텍처 설계]가 넘긴 항목)

### Q3-보충. 강제 로그아웃은 전파 이음매의 세 번째 얼굴이다

**분산 환경에서 ②③은 로컬에서 끝나지 않는다.** 끊어야 할 WS 세션이 다른 인스턴스에 붙어 있을 수 있다. 이는 [분산 전환 이음매 확정]이 하나로 통합한 **"인스턴스 간 전파"** 문제와 정확히 같다.

전파 이음매의 얼굴이 이제 셋이다:

1. 콘텐츠 채팅 / 시청 세션 JOIN·LEAVE
2. SSE 알림
3. **강제 로그아웃 시 WS 세션 종료** ← 이번에 추가

pub/sub 경로를 한 번 만들면 셋이 함께 풀린다는 구도는 그대로 유지된다.

### Q4. CSRF를 켠다 — **에이전트 추천 / 사용자 승인**

**형식적 요구가 아니다.** `POST /api/auth/refresh`와 `POST /api/auth/sign-out`은 **쿠키만으로 인증된다**(프론트가 refresh에서 Authorization 헤더를 의도적으로 빼는 것이 증거다). 공격자 사이트가 사용자의 브라우저를 시켜 이 둘을 호출할 수 있으므로 **CSRF 방어가 실제로 막는 대상이 존재한다.**

리프레시 쿠키에 `SameSite=Lax`를 함께 걸어 두 겹으로 막는다.

### Q5. 소셜 계정 연결 — **에이전트 추천 / 사용자 승인**

`(provider, providerId) → userId` 연결 테이블을 두고, **이메일이 일치하면 기존 계정에 자동 연결**한다.

- **구글** — 이메일이 검증된 값이라 자동 연결이 안전하다
- **카카오** — `{닉네임}_{회원ID}@kakao.com` 가상 이메일이라 기존 계정과 충돌할 일이 없다

`registrationId`는 프론트가 URL에 박아 넣으므로 정확히 **`google`, `kakao`** 여야 한다.

실패 시 `AuthenticationFailureHandler`에서 `/#/sign-in?error=oauth_failed&error_message=...`로 리다이렉트한다. 프론트가 그 두 쿼리 파라미터를 읽어 toast를 띄운다.

### Q6. 임시 비밀번호는 사용자 행에 — **에이전트 추천 / 사용자 승인**

해시와 만료 시각 두 컬럼. Redis도 가능하지만 **사용자 상태의 일부**이고 3분짜리를 별도 저장소로 뺄 이유가 없다. 로그인 검증에서 본 비밀번호 **또는** 유효한 임시 비밀번호를 허용하고, 비밀번호 재설정 시 파기한다. 프로토타입 규약대로 값은 `temporary1!!` 고정.

### Q7. 사용자 탈퇴는 구현하지 않는다 — **에이전트 추천 / 사용자 승인**

계약에 `DELETE /api/users/{userId}`가 없다. 접근 차단이 필요하면 `locked`가 그 역할을 한다. **[도메인 모델 확정]의 열린 항목이 이로써 닫힌다** — "탈퇴한 사용자의 리뷰·플레이리스트는 어떻게 되는가" 문제가 사라진다.
