# 실시간 WebSocket 아키텍처 설계

Type: grilling
Status: resolved
Blocked by: 01, 04

## Question

WebSocket 기반 실시간 기능 3종(같이 보기 세션, 콘텐츠 채팅, DM)의 구조를 정한다.

- **STOMP를 쓸 것인가** — `info.md`의 엔드포인트가 `SUBSCRIBE /sub/...`, `SEND /pub/...` 형태라 STOMP를 전제한 것으로 보인다. 확인하고 확정한다.
- **WebSocket 인증** — 클라이언트가 연결 시 액세스 토큰을 헤더에 넣는다. Spring WebSocket Security로 **어느 시점에**(핸드셰이크 / CONNECT 프레임) 인증할 것인가. 토큰이 연결 도중 만료되면?
- **시청 세션의 생명주기** — JOIN/LEAVE를 무엇으로 판정하는가. 연결이 비정상 종료되면? 브라우저 탭을 여러 개 열면? **시청자 수는 사용자 기준인가 연결 기준인가.**
- **채팅 메시지는 저장하지 않는다**(`info.md` 명시). 그러면 늦게 들어온 사람에게는 아무것도 안 보이는 것이 맞는가.
- **DM의 두 경로** — 활성 대화는 WebSocket, 다른 대화는 SSE. 한 메시지가 두 경로로 **중복 전달되지 않게 하는 기준**은 무엇인가. "활성"을 누가 판정하는가.
- 위 전부에 대해 **인스턴스가 2대일 때 무엇이 깨지는가**.

---

**[분산 전환 이음매 확정]이 이 티켓에 넘긴 것**

- **브로커는 Spring simple broker로 시작하고 발행 지점만 인터페이스 뒤에 둔다.** 이 미완성은 **의도된 것**이며, 인터페이스의 문서 주석에 "단일 인스턴스 전용이고 전환 시 브로커 릴레이로 교체한다"를 남긴다.
- **시청 세션 상태는 처음부터 Redis에 있다.** 따라서 이 티켓의 "인스턴스가 2대일 때 무엇이 깨지는가"에서 **시청자 수·시청자 목록은 깨지지 않는다.** 깨지는 것은 전파(채팅, JOIN/LEAVE 알림)뿐이다.
- **저장소 인터페이스는 계약이 규정한다** — ①여러 콘텐츠의 시청자 수 일괄 조회(N+1 금지) ②콘텐츠별 시청자 목록(이름 부분 검색 + 커서 + 총개수) ③사용자별 단건. **②의 이름 검색이 Redis 자료구조 선택을 구속한다.**
- **계약이 이미 답한 것** — `GET /api/users/{watcherId}/watching-sessions`가 단건을 반환하므로 **한 사용자는 최대 하나의 시청 세션**을 갖는다. 이 티켓의 "탭을 여러 개 열면?"은 이 규칙 위에서 답해야 한다.


## Answer

> **결정 주체 표시**: 사용자가 "올바른 방향 결정 추천해줘"로 판단을 위임했다. 아래 6건은 **에이전트가 정한 것**이다. 뒤집을 여지를 남겨 둔다.

### 프론트엔드 소스가 이미 답한 것 (결정이 아니라 사실)

`frontend/project-mopl-fe-1.0.5/src/lib/stores/{websocketStore,sseStore}.ts`와 각 페이지를 읽어 확인했다.

| 항목 | 사실 | 근거 |
| --- | --- | --- |
| 프로토콜 | **STOMP + SockJS**, 엔드포인트 `/ws` | `@stomp/stompjs` + `sockjs-client`, `new SockJS('/ws')` |
| WS 인증 시점 | **`CONNECT` 프레임의 `Authorization` 헤더** (핸드셰이크 아님) | `connectHeaders` |
| 하트비트 | 4000/4000, 재연결 지연 5000 | `heartbeatIncoming/Outgoing` |
| SSE 인증 | `Authorization` 헤더 — 그래서 `event-source-polyfill`을 쓴다(네이티브 `EventSource`는 헤더 불가) | `sseStore.ts` |
| SSE 이벤트 이름 | `notifications`, `direct-messages` | `addEventListener(...)` |

**① 클라이언트는 JOIN/LEAVE를 발행하지 않는다.** 전체 소스의 `/pub/` 목적지는 둘뿐이다 — `contents/{id}/chat`, `conversations/{id}/direct-messages`. 따라서 **서버가 STOMP 구독 이벤트에서 파생해야 한다**: `SessionSubscribeEvent` → JOIN, `SessionUnsubscribeEvent`·`SessionDisconnectEvent` → LEAVE.

**② DM의 두 경로는 중복이 아니라 상보적이다.** 티켓의 "중복 전달을 막는 기준은?"은 **틀린 질문이었다.** WebSocket 핸들러는 메시지를 대화창에 추가하고 읽음 처리하며, SSE 핸들러는 대화 *목록*의 미리보기·안 읽음 배지를 갱신하고 목록에 없는 대화를 가져온다. SSE 핸들러가 열린 대화를 명시적으로 처리한다(`hasUnread: selectedConversationId !== conversationId`).

**→ 서버는 둘 다 무조건 보낸다.** WS는 대화 토픽으로, SSE는 **수신자에게만**(발신자의 목록은 WS 핸들러가 갱신한다). "활성 대화 판정"은 서버의 일이 아니다.

### 결정

**Q1. 시청 세션의 키 — 사용자 기준 + 참조 카운트**

계약이 단건을 반환하므로 연결 기준은 불가능하다. 정리하면:

- **같은 콘텐츠를 여러 탭에서** → JOIN은 최초 1회만 브로드캐스트, LEAVE는 **마지막 구독이 사라질 때만**. 참조 카운트가 필요하다.
- **다른 콘텐츠를 새 탭에서** → 사용자당 세션이 하나뿐이므로 **이전 세션을 LEAVE 처리하고 대체**한다.

**Q2. 대화 토픽 구독 인가 — `ChannelInterceptor`에서 SUBSCRIBE 프레임 검사**

`/sub/conversations/{conversationId}/direct-messages`는 destination에 대화 id가 드러난다. **인가 검사가 없으면 로그인한 아무나 남의 DM을 실시간으로 엿본다.** 콘텐츠 채팅·시청 토픽은 공개(인증만)로 두고, 대화 토픽만 참여자 검사를 한다.

Spring Security의 선언적 메시지 인가가 아니라 인터셉터를 고른 이유: **"이 대화의 참여자인가"는 DB 조회가 필요한 동적 판단**이라 어차피 커스텀 로직이 들어간다. 선언 규칙과 커스텀 로직이 반씩 섞이는 것보다 한 곳에서 명시적으로 하는 편이 읽기 쉽다.

**Q3. `watcherCount` 갱신 — Redis는 즉시, DB는 주기적 동기화**

`WatchingSessionChange.watcherCount`가 JOIN/LEAVE 브로드캐스트마다 실린다. 브로드캐스트 값은 **Redis에서 즉시** 계산하고, `contents.watcher_count` 비정규화 컬럼은 **주기적으로 맞춘다.**

**이는 [도메인 모델 확정]의 "계산 필드는 트랜잭션 안에서 동기 갱신"과 의도적으로 다르다.** 성격이 다르기 때문이다 — 평점·구독자 수는 사용자의 명시적 행동이라 드물고 즉시 정확해야 하지만, JOIN/LEAVE는 **페이지를 드나들 때마다 발생**해 인기 콘텐츠일수록 같은 행에 쓰기가 몰린다. 목록의 숫자가 몇 초 늦는 것은 무해하다.

**Q4. 연결 도중 토큰 만료 — 연결 수명 동안 유효로 본다**

재연결 시 재인증된다. 강제 로그아웃·계정 잠금은 **그 순간 서버가 해당 사용자의 WS 세션을 직접 끊는 것**으로 처리한다([인증·인가와 토큰 무효화 설계]의 무효화 마커와 같은 지점에서). 매 메시지 재검증은 채팅 빈도에 비해 과하다.

**Q5. 채팅 미저장 — 그대로 간다**

`info.md`가 명시했고 같이 보기 채팅은 원래 지나가는 대화다. 늦게 들어온 사람에게 빈 화면이 보이는 것이 정상 동작이다.

**기록해 둘 것**: 분산 전환 후 채팅이 pub/sub으로 전파되면 **메시지 순서가 보장되지 않는다.** 저장하지 않으므로 순서를 복원할 방법도 없다. 감수하되 모르고 겪지는 않는다.

**Q6. SSE — `id:` 필드와 `LastEventId` 처리를 구현한다**

계약이 선언했고 알림이 이미 DB에 있어 구현 비용이 낮다. **단, 제공된 프론트엔드는 `LastEventId`를 보내지 않는다** — `sseStore.ts`는 재연결 시 그냥 다시 연결한다. 따라서 **이 경로는 프론트로 검증되지 않으며 직접 요청을 만들어 확인해야 한다.**

타임아웃은 넉넉히 두고 주기적 주석 이벤트로 연결을 유지한다.

### 다른 티켓으로 넘긴 것

- **Nginx의 SSE 버퍼링을 꺼야 한다** — 안 끄면 알림이 뭉쳐 오거나 아예 오지 않는다 → [로컬 개발·분산 환경 구성]
- **강제 로그아웃 시 WS 세션 종료** → [인증·인가와 토큰 무효화 설계]
- **`watcherCount`만 비동기 갱신이라는 예외** → [도메인 모델 확정]
- **채팅 순서 미보장** → [이음매를 감싸는 테스트 전략]
