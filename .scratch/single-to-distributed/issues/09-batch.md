# 콘텐츠 수집 배치 설계

Type: grilling
Status: resolved
Blocked by: 02, 03, 05

## Question

Spring Batch로 TMDB·The Sports DB 콘텐츠를 수집하는 Job을 설계한다. 두 조사 티켓이 확보한 사실을 근거로 삼는다.

- **Job 분할** — 소스별로 나눌 것인가, 하나의 Job에 Step으로 둘 것인가.
- **증분 vs 전량** — 조사 결과에 따라 갈린다. 증분이 불가능하면 무엇을 기준으로 중복을 걸러낼 것인가(외부 ID의 unique 제약?).
- **실패 처리** — 외부 API가 중간에 죽으면 어떻게 되는가. 재시도, skip 정책, 부분 성공을 어떻게 남길 것인가.
- **실행 트리거** — 스케줄러인가 수동인가. **인스턴스가 2대면 배치가 2번 도는 문제**를 어떻게 막을 것인가(이음매 티켓의 결정과 연결).
- **Actuator 커스텀 메트릭** — 무엇을 재야 의미가 있는가. 수집 건수, 실패율, 소요 시간.
- 배치 메타데이터 테이블을 서비스 DB에 둘 것인가 분리할 것인가.

---

**[TMDB API 조사] 해결로 확정된 입력** (이 티켓에서 다시 조사하지 말 것)

- 수집은 **일일 ID 익스포트 + `/changes`** 2축 + 델타 상세 조회 구조. `/discover` 전체 훑기는 500페이지 상한으로 불가능하다.
- 익스포트가 08:00 UTC(**17:00 KST**)에 완성되므로 배치 스케줄이 여기에 매인다.
- `/changes` 창을 **1일로 고정**하면 500페이지 상한 적용 여부라는 미확인 사항을 우회한다.
- 익스포트는 JSON Lines라 `FlatFileItemReader`로 스트리밍 가능(2026-08-31 영화 파일 1,238,234줄 — 메모리에 올리면 안 된다).
- **삭제 감지는 익스포트 diff로만 가능**하다. 삭제를 반영할 것인지가 이 티켓의 결정 사항.

**이 티켓이 추가로 답해야 할 것**

- **한국어 폴백 체인** — TMDB는 텍스트 폴백을 제공하지 않는다. `ko → en → original_*` 체인을 수집 시점에 적용해 저장할 것인가, 조회 시점에 적용할 것인가.


**[The Sports DB API 조사] 해결로 확정된 입력**

- **증분 수집 수단이 없다.** changed-since도 `dateUpdated`도 없다. `idEvent` + unique 제약 + **upsert**가 유일한 경로다. TMDB와 수집 전략이 근본적으로 다르므로 **Job 분할 판단에 직접 영향을 준다.**
- **429가 JSON이 아니다** — Cloudflare가 `text/plain` 본문 `error code: 1015`, `Retry-After: 119`를 준다. 순진한 역직렬화기는 이를 rate limit이 아니라 "깨진 JSON"으로 실패시킨다. **오류 처리 설계에서 이 경로를 별도로 다뤄야 한다.**
- **엔드포인트마다 같은 엔티티의 필드 수가 다르다**(49 / 30 / 20). DTO의 모든 필드가 nullable이어야 한다.
- 숫자가 전부 문자열로 오고, "없음"이 `null`과 `""`로 섞이며, `strSeason` 형식이 리그마다 다르다(추측 금지, 조회 필요). `strTimeLocal`은 틀린 레코드가 있어 `strTimestamp`만 신뢰한다.
- 실측 스로틀이 문서값(30/분)이 아닌 **43번째 요청**에서 걸렸다 — 무료 키는 **공유 버킷**이라 다른 사용자의 트래픽에 따라 시점이 달라진다. [스포츠 콘텐츠를 목적지에 둘 것인가]에서 무료 티어로 확정했으므로, **재현되지 않는 스로틀을 전제로 재시도 정책을 짜야 한다.**


**[도메인 모델 확정]이 이 티켓에 넘긴 것**

- **비정규화 집계값의 재계산이 필요하다.** `contents.watcher_count`는 Redis의 실시간 세션과 어긋날 수 있고(연결 비정상 종료, Redis 재시작), `average_rating`·`review_count`·`subscriber_count`도 동기 갱신이 실패하면 어긋난다. **정합성 재계산을 배치로 돌릴 것인가**, 돈다면 주기와 범위는?
- **콘텐츠 삭제와 배치 재수집이 충돌한다.** 관리자가 지운 콘텐츠를 배치가 다시 수집하면 되살아난다. 외부 ID를 기억해 재수집에서 제외할 것인가, 삭제 자체를 막을 것인가.
- **타입별 속성은 부속 테이블에 들어간다** — TMDB의 `tmdbId`·개봉일·러닝타임, 스포츠의 `idEvent`·경기 시각·팀·점수. **외부 ID의 unique 제약이 부속 테이블에 걸리므로** upsert 대상이 콘텐츠 본체가 아니라 부속 테이블이다.
- **태그는 별도 테이블 + 조인 테이블이다.** 수집 시 외부 API의 장르를 태그로 매핑할 텐데, 태그 정규화(대소문자·공백·중복)를 수집 경로에서 할 것인가.


**[알림·이벤트 파이프라인 설계]가 이 티켓에 넘긴 것**

- **안 읽은 알림 정리 배치**가 필요하다. 읽으면 삭제되므로(`DELETE /api/notifications/{id}`가 곧 읽음 처리) 보관 문제의 대부분은 사라지지만, **안 읽고 쌓이는 것**은 남는다. **보관 기간을 얼마로 할 것인가**를 이 티켓에서 정한다.
- **정합성 재계산 배치와 같은 Job으로 묶을 것인가**를 함께 판단한다. 둘 다 주기적 정리·보정 성격이라 따로 만들 이유가 없을 수 있다.


## Answer

> **결정 주체**: Q1은 사용자 선택. Q2~Q7은 에이전트가 추천하고 사용자가 승인했다. 배치 메타데이터 테이블 위치는 에이전트가 정했다(아래 명시).

### 조사가 정해준 숫자

| 사실 | 함의 |
| --- | --- |
| TMDB 영화 익스포트 **124만 줄**, 안전 레이트 20 req/s | 전량 상세 조회 시 **약 17시간** |
| `/discover` 페이지 상한 500 (=1만 건) | 전체 훑기 불가 → 익스포트 + `/changes` 2축 필수 |
| TheSportsDB **증분 수단 없음** | `idEvent` unique + upsert가 유일 |
| 무료 키 `eventsday` = **전 세계 하루 3건** | 스포츠는 1년 돌려도 **경기 1,000건 남짓** |
| SportsDB 429는 **평문** `error code: 1015`, `Retry-After: 119` | 상태코드·`Content-Type` 먼저 분기하지 않으면 "깨진 JSON"으로 오인 |

### Q1. 최초 백필은 `popularity` 상위만 — **(b), 사용자 선택**

**상위 30,000건**으로 시작한다(추천 범위 2~5만 중 에이전트가 잡은 값이며, 익스포트를 정렬해 자르는 구조라 **N 변경 비용이 0**이다).

전량(a)을 버린 이유 셋:

1. **학습 가치가 없다.** 증분 수집·실패 처리·레이트 제한은 3만 건에서 전부 겪는다.
2. **개발 반복을 죽인다.** 17시간 배치는 "돌려보고 고치기"가 불가능하다. 3만 건이면 20 req/s에서 **약 25분**이다.
3. **익스포트가 `popularity`를 주므로 공짜다.**

"최근 N년만"(c)은 익스포트 줄에 개봉일이 없어 **자르려면 124만 건을 다 조회해야 하는 자기모순**이라 탈락했다.

### Q2. 소스별 Job 분리, TMDB는 Step으로 — **에이전트 추천 / 사용자 승인**

```
tmdbSyncJob
  ├─ Step 1  익스포트 다운로드 → ID 존재 동기화 (신규·삭제 후보 판정)
  ├─ Step 2  /changes 조회 → 변경된 ID 수집
  └─ Step 3  Step 1·2가 뱉은 ID만 상세 조회 → upsert

sportsSyncJob
  ├─ Step 1  리그 화이트리스트 × 시즌 순회 (초기 적재)
  └─ Step 2  eventsday 오늘 ± N일 재조회

maintenanceJob   (Q7)
  ├─ Step 1  정합성 재계산
  ├─ Step 2  안 읽은 알림 정리
  └─ Step 3  묘비 정리
```

하나의 Job에 몰면 **한 소스의 실패가 다른 쪽을 막는다.** 실행 주기도 다르다 — TMDB는 익스포트 발행 시각(**KST 17:00**)에 매인다.

**스포츠 Step 2의 "± N일"이 핵심이다.** 증분 수단이 없고 경기는 끝난 뒤 점수가 채워지므로, 과거 며칠을 다시 긁는 것 외에 방법이 없다.

### Q3. 오류를 세 갈래로 가른다 — **에이전트 추천 / 사용자 승인**

| 갈래 | 처리 |
| --- | --- |
| **429** | 재시도. **`Retry-After` 헤더를 따른다** — SportsDB는 문서가 "1분"인데 실제 119초를 요구한다. TMDB는 헤더 유무가 미확인이라 **헤더 없이도 동작하는 백오프**가 필요하다. |
| **404** | 스킵. 삭제된 ID다. 재시도도 실패 기록도 무의미하다. |
| **5xx·타임아웃** | 재시도 후 실패 처리 |

**SportsDB의 429는 반드시 상태코드와 `Content-Type`을 먼저 보고 분기한다.** 바로 역직렬화하면 로그에 "rate limit"이 아니라 "malformed JSON"으로 남아 원인 추적에 시간을 쓴다.

**스로틀은 스레드 수가 아니라 요청 레이트로 건다** — TMDB의 동시 요청 제한이 문서화되어 있지 않다.

### Q4. 워터마크는 별도 도메인 테이블 — **에이전트 추천 / 사용자 승인**

소스별 마지막 성공 시각을 **별도 테이블**에 둔다. Spring Batch의 `JobParameter`·`ExecutionContext`에 기대지 않는 이유: **배치 메타데이터가 아니라 도메인 상태**다. 배치 메타 테이블을 지우고 다시 시작해도 "어디까지 수집했는가"는 남아야 한다.

**익스포트 축과 `/changes` 축은 워터마크를 따로 관리한다** — 기준점이 다르다(UTC 08:00 발행 vs 지난 24시간).

### Q5. 한국어 폴백은 수집 시점에 적용해 저장 — **에이전트 추천 / 사용자 승인**

`ko → en → original_*` 체인을 수집 시 적용한다. 조회 시점 적용은 원본 세 벌을 저장해야 하고(`ContentDto`에 자리도 없다) 목록 조회마다 분기가 붙는다. 결정적으로 **`title`은 `keywordLike` 검색과 정렬의 대상**이라 저장된 단일 값이어야 한다.

대가는 **번역이 나중에 추가돼도 즉시 반영되지 않는 것**인데, `/changes`가 그 변경을 잡아 자연히 갱신된다.

### Q6. 삭제된 콘텐츠는 묘비로 막는다 — **(a), 에이전트 추천 / 사용자 승인**

`(source, externalId)` 두 컬럼짜리 묘비 테이블을 두고 재수집에서 제외한다.

- **(b) 삭제 금지**는 계약에 `DELETE /api/contents/{contentId}`가 있으므로 위반이다.
- **(c) 되살아나게 두기**는 관리자가 지운 것이 다음 날 돌아오는 버그로 보인다.

### Q7. 유지보수 배치를 하나로 묶는다 — **에이전트 추천 / 사용자 승인**

정합성 재계산 · 안 읽은 알림 정리 · 묘비 정리 셋을 `maintenanceJob`의 Step으로 묶는다. 주기가 같고(일 1회) 서로 독립적이며, Job을 셋으로 나누면 스케줄 등록과 모니터링이 세 배가 된다.

**알림 보관 기간은 30일.** 읽으면 즉시 삭제되므로 30일 남은 알림은 사용자가 볼 의사가 없다고 본다.

**Actuator 커스텀 메트릭**은 Job별로 ①처리 건수 ②실패 건수 ③소요 시간 ④**마지막 성공 시각**을 노출한다. 네 번째가 중요하다 — **배치가 조용히 안 돌고 있는 상태**를 나머지 셋으로는 알 수 없다.

### 배치 메타데이터 테이블 위치 — **에이전트가 정함**

**서비스 DB에 함께 둔다.** 별도 DB는 이 규모에서 운영 부담만 늘리고, 같은 트랜잭션 매니저를 쓸 수 있어 재시작 일관성이 낫다.

### 분산 전환 시

**인스턴스가 2대면 배치가 2번 돈다.** [분산 전환 이음매 확정]에서 이 항목(7번)은 **"되돌리는 비용이 가장 낮으므로 전환 시점에 잠금을 추가한다"** 로 정해져 있다. 지금은 아무것도 하지 않는다.
