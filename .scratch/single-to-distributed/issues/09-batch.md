# 콘텐츠 수집 배치 설계

Type: grilling
Status: open
Blocked by: 02, 03, 05

## Question

Spring Batch로 TMDB·The Sports DB 콘텐츠를 수집하는 Job을 설계한다. 두 조사 티켓이 확보한 사실을 근거로 삼는다.

- **Job 분할** — 소스별로 나눌 것인가, 하나의 Job에 Step으로 둘 것인가.
- **증분 vs 전량** — 조사 결과에 따라 갈린다. 증분이 불가능하면 무엇을 기준으로 중복을 걸러낼 것인가(외부 ID의 unique 제약?).
- **실패 처리** — 외부 API가 중간에 죽으면 어떻게 되는가. 재시도, skip 정책, 부분 성공을 어떻게 남길 것인가.
- **실행 트리거** — 스케줄러인가 수동인가. **인스턴스가 2대면 배치가 2번 도는 문제**를 어떻게 막을 것인가(이음매 티켓의 결정과 연결).
- **Actuator 커스텀 메트릭** — 무엇을 재야 의미가 있는가. 수집 건수, 실패율, 소요 시간.
- 배치 메타데이터 테이블을 서비스 DB에 둘 것인가 분리할 것인가.

---

**[TMDB API 조사] 해결로 확정된 입력** (이 티켓에서 다시 조사하지 말 것)

- 수집은 **일일 ID 익스포트 + `/changes`** 2축 + 델타 상세 조회 구조. `/discover` 전체 훑기는 500페이지 상한으로 불가능하다.
- 익스포트가 08:00 UTC(**17:00 KST**)에 완성되므로 배치 스케줄이 여기에 매인다.
- `/changes` 창을 **1일로 고정**하면 500페이지 상한 적용 여부라는 미확인 사항을 우회한다.
- 익스포트는 JSON Lines라 `FlatFileItemReader`로 스트리밍 가능(2026-08-31 영화 파일 1,238,234줄 — 메모리에 올리면 안 된다).
- **삭제 감지는 익스포트 diff로만 가능**하다. 삭제를 반영할 것인지가 이 티켓의 결정 사항.

**이 티켓이 추가로 답해야 할 것**

- **한국어 폴백 체인** — TMDB는 텍스트 폴백을 제공하지 않는다. `ko → en → original_*` 체인을 수집 시점에 적용해 저장할 것인가, 조회 시점에 적용할 것인가.


**[The Sports DB API 조사] 해결로 확정된 입력**

- **증분 수집 수단이 없다.** changed-since도 `dateUpdated`도 없다. `idEvent` + unique 제약 + **upsert**가 유일한 경로다. TMDB와 수집 전략이 근본적으로 다르므로 **Job 분할 판단에 직접 영향을 준다.**
- **429가 JSON이 아니다** — Cloudflare가 `text/plain` 본문 `error code: 1015`, `Retry-After: 119`를 준다. 순진한 역직렬화기는 이를 rate limit이 아니라 "깨진 JSON"으로 실패시킨다. **오류 처리 설계에서 이 경로를 별도로 다뤄야 한다.**
- **엔드포인트마다 같은 엔티티의 필드 수가 다르다**(49 / 30 / 20). DTO의 모든 필드가 nullable이어야 한다.
- 숫자가 전부 문자열로 오고, "없음"이 `null`과 `""`로 섞이며, `strSeason` 형식이 리그마다 다르다(추측 금지, 조회 필요). `strTimeLocal`은 틀린 레코드가 있어 `strTimestamp`만 신뢰한다.
- 실측 스로틀이 문서값(30/분)이 아닌 **43번째 요청**에서 걸렸다 — 무료 키는 **공유 버킷**이라 다른 사용자의 트래픽에 따라 시점이 달라진다. [스포츠 콘텐츠를 목적지에 둘 것인가]에서 무료 티어로 확정했으므로, **재현되지 않는 스로틀을 전제로 재시도 정책을 짜야 한다.**


**[도메인 모델 확정]이 이 티켓에 넘긴 것**

- **비정규화 집계값의 재계산이 필요하다.** `contents.watcher_count`는 Redis의 실시간 세션과 어긋날 수 있고(연결 비정상 종료, Redis 재시작), `average_rating`·`review_count`·`subscriber_count`도 동기 갱신이 실패하면 어긋난다. **정합성 재계산을 배치로 돌릴 것인가**, 돈다면 주기와 범위는?
- **콘텐츠 삭제와 배치 재수집이 충돌한다.** 관리자가 지운 콘텐츠를 배치가 다시 수집하면 되살아난다. 외부 ID를 기억해 재수집에서 제외할 것인가, 삭제 자체를 막을 것인가.
- **타입별 속성은 부속 테이블에 들어간다** — TMDB의 `tmdbId`·개봉일·러닝타임, 스포츠의 `idEvent`·경기 시각·팀·점수. **외부 ID의 unique 제약이 부속 테이블에 걸리므로** upsert 대상이 콘텐츠 본체가 아니라 부속 테이블이다.
- **태그는 별도 테이블 + 조인 테이블이다.** 수집 시 외부 API의 장르를 태그로 매핑할 텐데, 태그 정규화(대소문자·공백·중복)를 수집 경로에서 할 것인가.


**[알림·이벤트 파이프라인 설계]가 이 티켓에 넘긴 것**

- **안 읽은 알림 정리 배치**가 필요하다. 읽으면 삭제되므로(`DELETE /api/notifications/{id}`가 곧 읽음 처리) 보관 문제의 대부분은 사라지지만, **안 읽고 쌓이는 것**은 남는다. **보관 기간을 얼마로 할 것인가**를 이 티켓에서 정한다.
- **정합성 재계산 배치와 같은 Job으로 묶을 것인가**를 함께 판단한다. 둘 다 주기적 정리·보정 성격이라 따로 만들 이유가 없을 수 있다.
