# 브랜치 전략과 CI/CD 결정

Type: grilling
Status: resolved
Blocked by: 11

## Question

혼자 하는 12주 프로젝트의 브랜치 전략과 CI/CD를 정한다. 팀 전략을 그대로 가져오면 과하다.

- **브랜치 전략** — 혼자인데 PR을 쓸 것인가. 쓴다면 **무엇을 얻기 위해서인가**(CI 통과 게이트? 변경 기록? 리뷰 습관?). `main` 직접 커밋과의 트레이드오프.
- **GitHub Actions** — PR 시 테스트 실행. 캐시 전략, 실행 시간, **Testcontainers를 CI에서 돌릴 수 있는가**.
- **커버리지 배지** — jacoco 결과를 어떻게 배지로 만들 것인가. 외부 서비스에 맡길지 자체 생성할지.
- **배포 워크플로** — AWS는 검증할 때만 올린다. 그렇다면 배포는 자동인가 **수동 트리거**인가. 자격증명을 어떻게 넘길 것인가.

이 결정들은 12주 내내 매일 부딪힌다. 마찰이 큰 쪽을 고르면 지켜지지 않고, 지켜지지 않는 전략은 없는 것만 못하다.

---

**[이음매를 감싸는 테스트 전략]이 넘긴 것**

- **`jacocoTestCoverageVerification`이 `check`에 연결되어 있지 않다.** 80% 규칙이 선언만 되어 있고 `./gradlew build`로는 돌지 않는다. **`check.dependsOn jacocoTestCoverageVerification` 배선이 이 티켓의 실행 항목이다.**
- **커버리지 제외 대상**(DTO·설정 클래스·생성 코드)의 구체 목록을 여기서 정한다. 배지를 실제로 만들 때 함께 정하는 것이 맞다.
- **CI는 Testcontainers로 PostgreSQL·Redis를 띄우고, 전환 이후에는 Kafka까지 띄운다.** 계약 테스트를 단일·분산 두 모드로 모두 돌려야 분산 구현의 커버리지가 확보된다 → **CI 실행 시간이 이 결정에 직접 걸린다.**
- **외부 API를 때리는 테스트는 별도 태그로 분리되어 CI에서 제외된다.** CI 워크플로가 그 태그를 빼고 실행해야 한다.


## Answer

> **결정 주체**: 6건 모두 에이전트가 추천하고 사용자가 승인했다("추천하는거로 결정해줘").

### 출발점 사실

저장소는 public, 이슈 활성화, **`main` 브랜치 보호 없음**, `.github` 디렉토리 없음. `gh` 토큰에 `workflow` 스코프가 있어 워크플로 생성·푸시에 추가 권한이 필요 없다.

사용자는 이미 **이슈 → 브랜치 → PR → 리뷰노트** 흐름의 도구를 갖고 있다(`/draft-issue`, `/start-issue`, `/draft-pr`, `/pr-review-note`). 이 티켓의 결정은 그 흐름과 어긋나지 않아야 실제로 지켜진다.

### Q1. 기능 브랜치 + PR, 승인 없이 셀프 머지

`info.md`가 "브랜치 전략 수립"과 "**PR 생성 시** 자동 테스트"를 요구하므로 PR 자체는 사실상 정해져 있다. PR로 얻는 것 셋:

1. **CI 게이트** — 테스트가 통과해야 `main`에 들어간다
2. **변경 단위 기록** — 이 프로젝트에서 특히 값이 크다. **이음매 전환마다 PR 하나**면 "전파를 분산으로 바꿈"이 **되돌릴 수 있는 하나의 단위**가 된다. 전환이 잘못됐을 때 revert 대상이 명확하다
3. **기존 도구와 맞는다**

**`main`에는 필수 상태 검사만 걸고 승인 요구는 걸지 않는다.** 혼자인데 승인을 요구하면 매번 우회하게 되고, **우회하는 규칙은 없느니만 못하다.**

브랜치 이름은 **`feat/<이슈번호>-<슬러그>`** (그 외 `fix/`, `refactor/`, `docs/`, `chore/`).

**봇 리뷰어(CodeRabbit 등)를 붙인다.** 혼자라 사람 리뷰어가 없으니 리뷰 습관의 빈자리를 메운다. `/pr-review-note` 스킬이 `--with-bot`으로 봇 리뷰를 수집하므로 학습 기록까지 이어진다.

### Q2. CI는 PR과 `main` 푸시에서 `./gradlew build` 하나

`ubuntu-latest`에 Docker가 있어 **Testcontainers가 그대로 돈다.** Gradle 캐시는 `setup-java`의 `cache: gradle`로 충분하다.

**실행 시간이 이 결정의 핵심 위험이다.** 지금은 PostgreSQL + Redis 두 컨테이너지만, 전환 이후 **Kafka가 붙고 계약 테스트를 단일·분산 두 모드로 돌려야 한다**([이음매를 감싸는 테스트 전략]의 커버리지 요구). Kafka 컨테이너는 느리다.

**→ 지금은 단일 job으로 시작하고, 전환 시점에 단일 모드 / 분산 모드 job을 병렬로 쪼갠다.** 미리 쪼개면 쓰지도 않는 복잡도만 생긴다.

**외부 API를 때리는 테스트는 `@Tag("external")`로 묶어 CI에서 제외한다.**

### Q3. 커버리지 배지는 Gist + shields.io endpoint

CI가 jacoco XML을 파싱해 gist에 JSON을 쓰고 README가 shields.io로 렌더한다.

- **Codecov 등 외부 서비스**를 버린 이유: 계정 연동과 토큰이 하나 더 늘고, 강점인 diff coverage·PR 코멘트가 **혼자 하는 프로젝트에서 값을 별로 못 한다.**
- **배지 SVG 커밋**을 버린 이유: 푸시마다 생성 파일 커밋이 쌓여 히스토리가 지저분해진다.

### Q4. 80% 게이트는 처음부터 켜되 제외 규칙으로 초기 마찰을 없앤다

제외 대상을 빼면 남는 건 실제 로직뿐이고, **TDD로 가기로 했으므로 로직에는 항상 테스트가 먼저 있다.** 나중에 켜기로 미루면 그 시점에 밀린 부채가 한꺼번에 나타나고 결국 게이트를 끄게 된다.

**제외 목록의 출발점**: `**/dto/**`, `**/config/**`, `MoplApplication`. [이음매를 감싸는 테스트 전략]이 "코드가 없는 상태에서 제외 규칙을 쓰면 나중에 안 맞는다"고 미뤄뒀으나, **이 셋은 패키지 구조가 이미 잡혀 있어 지금 정할 수 있다.** 나머지는 실제로 걸릴 때 추가한다.

**`check.dependsOn jacocoTestCoverageVerification` 배선**이 이 티켓의 실행 항목이다.

### Q5. 배포는 `workflow_dispatch` 수동 트리거, 자격증명은 OIDC

자동 배포는 **상시 떠 있는 인프라를 전제**하는데 그 전제가 없다("AWS는 검증할 때만 올리고 내린다"). 푸시마다 배포하려 들면 없는 대상에 배포하다 실패한다.

**자격증명은 OIDC(GitHub → AWS IAM Role).** 장기 액세스 키를 시크릿에 넣지 않는다 — public 저장소라 더욱 그렇고, 키 유출 사고의 대부분이 이 경로다.

**배포 워크플로의 범위는 "이미지 빌드 + ECS 서비스 갱신"까지.** 인프라 프로비저닝(태스크 정의, 로드밸런서, ElastiCache)은 지도의 안개 "AWS 배포 형상"이 정해져야 손댈 수 있다.

### Q6. 커밋린트·정적 분석은 넣지 않는다

혼자 하는 프로젝트에서 커밋린트는 마찰만 만들고, 이미 일관된 형태로 쓰고 있어 규칙 없이도 지켜진다. 정적 분석(Checkstyle, SpotBugs)도 지금은 넣지 않는다 — **CI 실행 시간이 이미 Testcontainers로 늘어날 예정**이라 값이 확실하지 않은 것을 미리 얹지 않는다.

### 이 티켓에서 실행하지 않은 것

- **브랜치 보호 설정** — 필수 상태 검사를 걸려면 **검사할 워크플로가 먼저 존재해야 한다.** 워크플로 작성은 구현이므로, 보호 설정은 그 뒤에 붙는다.
- **봇 리뷰어 설치** — GitHub App 설치는 사용자 계정의 외부 작업이다.
- **`check` 배선과 워크플로 파일** — 구현 항목.

## 보충 (2026-09-05, 1주차 구현 중)

**봇 리뷰어를 붙이지 않는다 — 사용자 결정.** Q1이 "봇 리뷰어(CodeRabbit 등)를 붙인다"고 정했으나 사용자가 쓰지 않기로 했다. 저장소에 설치된 봇이 없고 설정 파일도 없으므로, 되돌리는 것이 아니라 붙지 않은 상태 그대로 간다.

**리뷰 습관의 빈자리는 PR 올리기 전 로컬 `/code-review`로 메운다.** 봇과 달리 PR에 자동으로 걸리지 않으므로 **CI 게이트가 아니라 습관에 의존하는 것이 대가다.** 빠뜨려도 아무것도 막지 않는다.

**딸려오는 것 둘**

- `/pr-review-note` 스킬은 이번 프로젝트에서 쓰이지 않는다. 사람 리뷰어도 봇도 없어 수집할 리뷰가 0건이다.
- "이 티켓에서 실행하지 않은 것"의 **봇 리뷰어 설치 항목이 무효**가 된다. 나머지 둘(브랜치 보호, `check` 배선과 워크플로 파일)은 실행됐으므로 이 티켓에 남은 미실행 항목은 없다.
