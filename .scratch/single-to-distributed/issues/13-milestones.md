# 12주 마일스톤 구획

Type: grilling
Status: resolved
Blocked by: 04, 05

## Question

12주를 어떻게 끊을 것인가. 이음매와 도메인 모델의 결정을 받아 실제 순서를 정한다.

- **단일 인스턴스 완성까지 몇 주** — 그리고 "완성"의 기준은 무엇인가. 프론트가 붙어서 도는 것?
- **어느 기능부터** — 인증 → 콘텐츠 → 평점·플레이리스트 → 관계 → 실시간 → 알림 순으로 가로로 쌓을 것인가, 아니면 세로로 얇게 한 흐름을 끝까지 뚫고 넓혀갈 것인가.
- **분산 전환을 언제 시작할 것인가** — 모든 기능이 끝난 뒤인가, 아니면 일부 기능만 있을 때 한 번 겪어보고 나머지를 분산 전제로 만들 것인가. **후자가 이번 연습의 주제에 더 가까울 수 있다.**
- **AWS를 언제 처음 올려볼 것인가** — 마지막에 몰면 반드시 터진다.
- 12주 중 얼마를 버퍼로 남길 것인가.

---

**[콘텐츠 수집 배치 설계]가 넘긴 일정 항목**

- **최초 백필은 TMDB `popularity` 상위 30,000건**이며 20 req/s에서 **약 25분**이 걸린다. 하루에 여러 번 돌릴 수 있으므로 일정의 병목이 아니다.
- **스포츠는 시간이 곧 데이터다.** 무료 키의 `eventsday`가 하루 3건을 주므로, 정기 Job을 **일찍 켜둘수록** 경기 데이터가 쌓인다. 12주 후반에 시작하면 수십 건에 그친다 — **스포츠 수집 Job은 앞쪽 마일스톤에 배치해야 한다.**
- TMDB 정기 Job은 익스포트 발행 시각(**KST 17:00**)에 매인다.


**[로컬 개발·분산 환경 구성]이 넘긴 일정 항목**

- **Dockerfile이 전환 검증 시점보다 먼저 필요하다.** 로컬 분산을 이미지 2개로 구성하기로 했으므로, 전환을 처음 시도하는 마일스톤 앞에 Dockerfile 작성이 들어가야 한다. ECS 배포와 같은 이미지를 쓰므로 이때 만든 것이 그대로 간다.
- **전환은 이음매 단위로 쪼개져 있다**(프로퍼티 축별 스위치). 즉 "분산 전환"을 한 덩어리 마일스톤으로 잡을 필요가 없고, **전파 → 이벤트 발행 → 파일 저장 → 캐시**를 각각 별도로 배치할 수 있다.


**[이음매를 감싸는 테스트 전략]이 넘긴 일정 항목**

- **"단일 모드에서는 전파되지 않는다"를 통과로 쓰는 알람 테스트**는 각 이음매의 단일 구현을 만드는 시점에 함께 작성된다. 전환 마일스톤에서 이 테스트가 실패로 바뀌는 것이 **전환 완료의 판정 기준**이다.
- 따라서 마일스톤마다 **"어떤 알람 테스트가 뒤집혔는가"** 로 진척을 확인할 수 있다.


**[브랜치 전략과 CI/CD 결정]이 넘긴 일정 항목**

- **이음매 전환마다 PR 하나**가 되도록 마일스톤을 끊는다. 전환이 잘못됐을 때 revert 대상이 명확해진다.
- **CI 실행 시간이 전환 이후 늘어난다** — Kafka 컨테이너가 붙고 계약 테스트를 두 모드로 돌린다. 전환 마일스톤에 **CI job 병렬 분리** 작업을 함께 넣어야 한다.
- **초기 세팅 작업이 1주차에 몰린다**: 워크플로 작성, `check` 배선, 커버리지 배지, 브랜치 보호, 봇 리뷰어 설치. 기능 개발 시작 전에 하루 정도가 필요하다.
- **AWS 배포 워크플로는 `workflow_dispatch` 수동**이므로 "언제 처음 올려보는가"가 일정에 명시적으로 들어가야 한다. 자동이 아니므로 잊으면 그냥 안 한다.


## Answer

> **결정 주체**: 5건 모두 에이전트가 추천하고 사용자가 승인했다("추천해주는 방향으로 갈게"). 주차 배치표도 에이전트 제안을 그대로 채택했다.

### Q1. 세로로 얇게 뚫고 넓힌다

결정적인 이유는 **프론트엔드가 이미 있다**는 것이다. 인증 → 콘텐츠 목록까지 뚫으면 **브라우저에서 곧바로 확인된다.** 가로로 쌓으면(모든 엔티티 → 모든 서비스 → 모든 컨트롤러) 마지막에 프론트를 붙일 때 **틀린 것을 한꺼번에 발견**하고, 그때는 되돌릴 시간이 없다.

### Q2. 기능이 절반쯤 있을 때 첫 전환을 겪는다

1. **목적지가 "전환을 겪어보는 것"** 이지 기능 완성이 아니다
2. **이음매가 프로퍼티로 쪼개져 있어**([로컬 개발·분산 환경 구성]) 하나씩 밟을 수 있다 — 전부 만들 때까지 기다릴 이유가 없다
3. **첫 전환 대상인 전파는 인증 + 콘텐츠만 있으면 만들 수 있다**
4. **늦게 하면 전환이 마지막 2주에 몰린다.** 거기서 터지면 12주가 통째로 끝난다

그리고 **첫 전환을 겪고 나면 나머지 기능을 분산 전제로 설계**하게 된다. 알림·DM을 만들 때 "인스턴스가 늘면 어떻게 되지"가 자동으로 떠오른다 — 겪어본 사람만 그렇다.

### Q3. AWS는 두 번 올린다. 첫 번째는 **단일 인스턴스**다

분산 배포를 처음 시도하면 실패했을 때 **"배포가 안 되는 것"과 "분산이 안 되는 것"이 섞인다.** 원인을 가르는 데만 며칠이 간다.

- **1차 (4주차)** — 단일 인스턴스를 ECS에 올렸다 내린다. **파이프라인·OIDC·이미지·태스크 정의만 검증**한다
- **2차 (7주차)** — Nginx + 인스턴스 2대

1차를 통과해 두면 2차 실패 시 **원인이 분산 쪽이라는 게 확실**해진다.

### Q4. "단일 완성"의 기준 — 경로 32개 전부가 아니다

**프론트가 붙어서 주요 흐름이 브라우저에서 도는 것.** 관리자 기능이나 예외적 경로 몇 개가 비어 있어도 완성으로 친다. **완벽을 기준으로 잡으면 전환에 영영 못 간다.**

### Q5. 마지막 2주를 버퍼로 비운다

"여유"가 아니라 **터질 것에 대한 예산**이다. AWS와 분산은 예상보다 오래 걸린다 — 예외 없이. 버퍼가 없으면 12주차에 "동작하지 않는 상태"로 끝난다.

### 확정된 12주 형태

| 주 | 내용 | 이 주의 확인 지점 |
| --- | --- | --- |
| **1** | 세팅 — CI 워크플로, `check` 배선, 배지, 브랜치 보호, 봇 리뷰어, docker-compose, 프로퍼티 스위치 뼈대, **TMDB 키 발급** / 인증 착수 | CI가 초록으로 돈다 |
| **2** | 인증 완성 — JWT·refresh·CSRF·소셜 로그인·강제 로그아웃 | **브라우저에서 로그인이 된다** |
| **3** | 콘텐츠 + 배치 — TMDB 백필 3만 건, **스포츠 정기 Job 켜기** | 콘텐츠 목록이 프론트에 뜬다 |
| **4** | **AWS 1차 배포(단일)** — 올렸다 내림 / 리뷰·플레이리스트 | 파이프라인이 동작한다 |
| **5** | 실시간 — 시청 세션 + 콘텐츠 채팅 (단일 구현) | 탭 두 개로 채팅이 보인다 |
| **6** | **첫 전환 — 전파 이음매** / 로컬 분산(이미지 2개 + Nginx), CI job 분리 | **알람 테스트가 뒤집힌다** |
| **7** | **AWS 2차 배포(분산)** — Nginx + 인스턴스 2대 | 두 인스턴스에서 채팅이 보인다 |
| **8** | 팔로우 · 구독 · DM | 관계 기능이 돈다 |
| **9** | 알림 — SSE (**분산 전제로 설계**) | 알림이 두 인스턴스에서 온다 |
| **10** | 나머지 전환 — 이벤트 발행→Kafka, 파일 저장→S3, 캐시→Redis | 알람 테스트 3개가 더 뒤집힌다 |
| **11–12** | **버퍼** + 마무리 (README, 배지, 문서) | — |

**3주차에 스포츠 Job을 켜는 것이 중요하다.** 무료 키가 하루 3건을 주므로 **켜둔 날수가 곧 데이터**다. 3주차면 12주차에 190건쯤, 9주차면 60건이다.

**6주차가 이 지도의 절정이다.** 알람 테스트가 실패로 바뀌는 순간이 전환의 증거다.

### 이 결정이 안개에서 졸업시킨 것

주차 배치가 정해지면서 두 항목이 **"결정하지 않으면 그 주에 막힌다"** 는 것이 분명해졌다.

- **예외·에러 응답 계약** → 2주차 인증부터 필요하다 → [예외·에러 응답 계약 확정]
- **AWS 배포 형상** → 4주차 1차 배포 전에 필요하다 → [AWS 배포 형상 확정]

**"분산 전환의 절차"는 이 티켓이 답했으므로 안개에서 제거한다.**


**[AWS 배포 형상 확정]이 넘긴 일정 항목**

- **4주차 1차 배포 전에 teardown 워크플로가 함께 있어야 한다.** 올리는 워크플로만 만들고 내리는 것을 손으로 하면 NAT Gateway를 빠뜨린다. **둘은 짝으로 만든다.**
- **RDS 스냅샷 복원에 10~20분**이 걸리므로 검증 세션은 반나절 단위로 잡는다.
- **7주차 2차 배포에는 Nginx 설정이 걸린다** — SSE 버퍼링 끄기, SockJS 폴백 트랜스포트 통과. 로컬 분산(6주차)에서 이미 맞춰둔 설정을 그대로 옮긴다.
