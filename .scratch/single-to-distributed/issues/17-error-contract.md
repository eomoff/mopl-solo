# 예외·에러 응답 계약 확정

Type: grilling
Status: resolved

## Question

[12주 마일스톤 구획]이 이 항목을 안개에서 졸업시켰다. **2주차 인증부터 필요하다** — 로그인 실패, 토큰 만료, 권한 부족이 전부 에러 응답이고, 프론트가 그 형태에 맞춰 이미 동작한다.

계약의 `ErrorResponse`는 `{ exceptionName, message, details }` 세 필드다. 여기서 갈리는 것들:

- **`exceptionName`에 무엇을 넣을 것인가** — 자바 예외 클래스명을 그대로 노출하면 내부 구조가 새어나간다. 도메인 에러 코드를 쓸 것인가?
- **`message`는 사용자에게 보여줄 문장인가 개발자용 설명인가** — 프론트가 이걸 toast로 띄우는지 확인이 필요하다(**프론트 소스에서 확인할 수 있다**).
- **`details`(object)에 무엇을 담을 것인가** — Bean Validation 위반 시 필드별 메시지가 자연스러운 자리다.
- **커스텀 예외 계층을 어떻게 설계할 것인가** — `info.md`가 "커스텀 예외를 구조적으로 설계"를 요구한다. 도메인별로 나눌 것인가, 성격(찾을 수 없음/권한 없음/중복)별로 나눌 것인가.
- **상태코드 매핑** — 계약이 경로마다 400/401/403/404/500을 선언한다. **특히 401과 403의 구분이 중요하다**: [인증·인가와 토큰 무효화 설계]에서 확인했듯 프론트는 **401에서만 토큰 재발급**을 건다. 권한 부족에 401을 주면 무한 재발급 루프가 된다.
- **`@RestControllerAdvice` 하나로 갈 것인가**, 도메인별로 나눌 것인가.

**계약이 선언한 상태코드를 전수 확인하는 것이 이 티켓의 첫 작업이다** — `contract/api.json`에서 경로별 응답 코드를 뽑으면 무엇을 만들어야 하는지가 그대로 나온다.


## Answer

> **결정 주체**: Q1은 사용자 선택(에이전트 추천과 일치). Q2~Q6은 에이전트가 추천하고 사용자가 승인했다.

### 전수 확인 결과 — 계약이 쓰는 상태코드는 다섯 개뿐

| 코드 | 등장 | 비고 |
| --- | --- | --- |
| 400 | 44 | 사실상 모든 오퍼레이션 |
| 401 | 41 | **미선언 4개**: `GET /api/auth/csrf-token`, `POST /api/auth/reset-password`, `POST /api/auth/sign-out`, `GET /api/sse` |
| 403 | **15** | 정확히 소유권·역할이 걸리는 곳 |
| 404 | **5** | `reset-password`, `conversations/with`, `conversations/{id}`, `follows/followed-by-me`, `users/{userId}` |
| 500 | 44 | |

**409(Conflict)가 없다.** 그리고 **`GET /api/contents/{contentId}`와 `GET /api/playlists/{playlistId}`에 404가 없다.**

`GET /api/sse`는 **200만 선언**한다(SSE라 에러를 표현할 자리가 없다). `sign-out`에 401이 없는 것은 **이미 로그아웃 상태여도 성공 처리**한다는 뜻으로 읽는다.

### 프론트엔드는 서버의 `message`를 단 한 번도 표시하지 않는다

```ts
// SignInForm.tsx
} catch (error) {
  console.error("Faile to sign in.", error);
  toast.error('로그인에 실패했습니다. 다시 시도해주세요.');   // 하드코딩
}
```

모든 폼이 같다. 스토어 공통 경로(`actions.ts`, `utils.ts`)는 `(error as Error).message`를 읽는데 이는 **Axios의 메시지**("Request failed with status code 400")이지 서버 응답 본문이 아니다. `ErrorResponse`를 타입으로 임포트하는 화면 코드조차 없다.

**→ `message`와 `details`는 이 클라이언트에서 사용자 눈에 닿지 않는다.**

### Q1. 404를 선언하지 않은 조회에서는 **400**을 준다 — **(a), 사용자 선택**

1. **지도의 원칙이 "계약이 이긴다"** 이다. 여기서 한 번 넘어서면 어디까지 넘어설지 기준이 사라진다.
2. **404를 선언한 5곳이 따로 있다는 것이 우연이 아니다.** 계약 작성자가 의도적으로 구분했다고 읽는다.
3. **프론트 동작이 어차피 같다.** `client.ts`가 특별 처리하는 것은 401뿐이고 나머지는 `catch`로 떨어져 하드코딩 메시지를 띄운다.

**같은 논리로 중복도 400이다** — 이메일 중복 가입, 중복 팔로우, 같은 콘텐츠 두 번 평점. 409가 계약에 없다.

### Q2. `message`는 개발자용으로 최적화한다

로그에 남길 내용과 같은 것을 담는다 — 어떤 리소스의 어떤 id에서 무엇이 틀렸는지. **사용자용 문구를 다듬는 데 시간을 쓰지 않는다.**

**두 가지는 지킨다**: ①비밀번호·토큰·이메일 전문 같은 민감정보를 넣지 않는다 ②`500`에서 **스택트레이스나 내부 경로를 노출하지 않는다.** 실제 배포되고 저장소가 public이다.

### Q3. `exceptionName`에는 **도메인 에러 코드**를 넣는다

`CONTENT_NOT_FOUND` 형태. 자바 클래스명을 그대로 노출하면 **리팩터링할 때 값이 바뀌어** 계약이 아닌데 계약처럼 굳고, 내부 패키지 구조가 새어나간다. 에러 코드는 **로그 검색이 쉽고** 나중에 클라이언트가 분기할 일이 생기면 그대로 쓸 수 있다. 클래스명은 어차피 서버 로그의 스택트레이스에 남는다.

### Q4. 401과 403을 절대 섞지 않는다

**401 = 인증 실패(토큰 없음·만료·무효화), 403 = 인증은 됐으나 권한 없음.**

권한 부족에 401을 주면 프론트가 재발급을 걸고, 재발급은 성공하고, 다시 403… **무한 루프**가 된다.

**⚠️ Spring Security의 함정**: 익명 사용자가 보호된 자원에 접근할 때 설정에 따라 `AccessDeniedException`이 나서 **403이 나간다.** 그러면 프론트는 재발급을 걸지 않고 그냥 실패로 처리해, **토큰이 만료됐는데 로그인 상태로 멈춰 있는** 상태가 된다. **`AuthenticationEntryPoint`를 명시적으로 설정해 미인증은 반드시 401이 되게 한다.**

**403은 계약이 선언한 15곳에서만 내보낸다** — 콘텐츠 CRUD(어드민), 플레이리스트·리뷰 수정/삭제(소유자), 팔로우 삭제(본인), 사용자 목록·권한·잠금(어드민), 비밀번호 변경(본인).

### Q5. 성격별 베이스 + 도메인별 구체, `@RestControllerAdvice`는 하나

성격(찾을 수 없음 / 권한 없음 / 잘못된 요청 / 중복)이 **상태코드 매핑을 결정**하고, 도메인이 **에러 코드를 결정**한다.

- 도메인별로만 나누면 도메인마다 상태코드 매핑을 반복하게 된다.
- 성격별로만 나누면 에러 코드를 구분할 자리가 없다.

`@RestControllerAdvice`를 도메인별로 나누면 어느 핸들러가 잡는지 추적이 어려워지고, 지금은 매핑 규칙이 단순하다.

### Q6. `details`에는 Bean Validation 위반 시 `{필드명: 메시지}`

그 외에는 비운다. 프론트가 읽지 않지만 **개발 중 값이 크다** — 어떤 필드가 왜 걸렸는지 응답만 보고 알 수 있다.
