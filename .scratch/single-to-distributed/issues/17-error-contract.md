# 예외·에러 응답 계약 확정

Type: grilling
Status: open

## Question

[12주 마일스톤 구획]이 이 항목을 안개에서 졸업시켰다. **2주차 인증부터 필요하다** — 로그인 실패, 토큰 만료, 권한 부족이 전부 에러 응답이고, 프론트가 그 형태에 맞춰 이미 동작한다.

계약의 `ErrorResponse`는 `{ exceptionName, message, details }` 세 필드다. 여기서 갈리는 것들:

- **`exceptionName`에 무엇을 넣을 것인가** — 자바 예외 클래스명을 그대로 노출하면 내부 구조가 새어나간다. 도메인 에러 코드를 쓸 것인가?
- **`message`는 사용자에게 보여줄 문장인가 개발자용 설명인가** — 프론트가 이걸 toast로 띄우는지 확인이 필요하다(**프론트 소스에서 확인할 수 있다**).
- **`details`(object)에 무엇을 담을 것인가** — Bean Validation 위반 시 필드별 메시지가 자연스러운 자리다.
- **커스텀 예외 계층을 어떻게 설계할 것인가** — `info.md`가 "커스텀 예외를 구조적으로 설계"를 요구한다. 도메인별로 나눌 것인가, 성격(찾을 수 없음/권한 없음/중복)별로 나눌 것인가.
- **상태코드 매핑** — 계약이 경로마다 400/401/403/404/500을 선언한다. **특히 401과 403의 구분이 중요하다**: [인증·인가와 토큰 무효화 설계]에서 확인했듯 프론트는 **401에서만 토큰 재발급**을 건다. 권한 부족에 401을 주면 무한 재발급 루프가 된다.
- **`@RestControllerAdvice` 하나로 갈 것인가**, 도메인별로 나눌 것인가.

**계약이 선언한 상태코드를 전수 확인하는 것이 이 티켓의 첫 작업이다** — `contract/api.json`에서 경로별 응답 코드를 뽑으면 무엇을 만들어야 하는지가 그대로 나온다.
