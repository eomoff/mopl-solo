# AWS 배포 형상 확정

Type: grilling
Status: resolved

## Question

[12주 마일스톤 구획]이 이 항목을 안개에서 졸업시켰다. **4주차 1차 배포(단일 인스턴스) 전에 필요하다.**

지도의 제약을 다시 확인하고 시작한다 — **AWS는 검증할 때만 올리고 내린다**(상시 과금 회피). 따라서 **"내렸다 올려도 보존되어야 하는 상태가 무엇인가"** 가 이 티켓의 중심 질문이다.

- **무엇이 휘발되어도 되는가** — [분산 전환 이음매 확정]에 따라 시청 세션은 Redis에 있어 사라진다(허용 가능한가?). 알림·DM·사용자·콘텐츠는 DB라 남아야 한다.
- **DB를 어떻게 할 것인가** — RDS를 상시 띄우면 그 자체로 과금이다. 내렸다 올릴 때 데이터를 어떻게 유지하는가? 스냅샷? 아니면 배포 검증 때마다 배치로 다시 채우는가(백필 25분)?
- **1차 배포(단일)의 최소 형상** — ECS 서비스 1개 + DB + Redis. 로드밸런서가 필요한가, 퍼블릭 IP로 충분한가?
- **2차 배포(분산)의 형상** — Nginx 리버스 프록시를 ECS 태스크로 둘 것인가 ALB로 대체할 것인가. `info.md`는 **Nginx**를 명시한다.
- **Kafka·Redis를 관리형(Confluent Cloud, ElastiCache)으로 쓸 것인가**, ECS 태스크로 띄울 것인가. 관리형은 과금이 상시다.
- **이미지 저장소**(ECR)와 태그 전략.
- **비용 상한을 어떻게 지킬 것인가** — 예산 알림, 내리는 것을 잊었을 때의 안전장치.

[브랜치 전략과 CI/CD 결정]에서 **배포는 `workflow_dispatch` 수동 트리거, 자격증명은 OIDC**로 이미 정해졌다. 이 티켓은 **무엇을 향해 배포하는가**를 정한다.


## Answer

> **결정 주체**: Q1은 사용자 선택으로 **에이전트 추천과 다르다**(추천은 (a) 퍼블릭 서브넷). Q2~Q6은 에이전트가 추천하고 사용자가 승인했다.

### 먼저 — 무엇이 보존되어야 하는가

지도의 앞선 결정들이 이 질문에 이미 답해 놓았다.

| 저장소 | 담긴 것 | 내렸을 때 |
| --- | --- | --- |
| **DB** | 사용자·콘텐츠·리뷰·플레이리스트·팔로우·대화·DM·알림·워터마크·묘비 | **보존 필요** |
| **Redis** | 시청 세션, 무효화 목록(TTL 15분) | **전부 잃어도 됨** |
| **S3** | 프로필 이미지, 콘텐츠 썸네일 | 내려도 남음 (스토리지 요금만) |

**Redis에 영속이 필요한 것이 하나도 없다**는 사실이 [분산 전환 이음매 확정]과 [인증·인가와 토큰 무효화 설계]에서 자동으로 따라온다. 이것이 Q3의 답을 정했다.

### Q1. 프라이빗 서브넷 + NAT Gateway — **(b), 사용자 선택 (에이전트 추천은 (a))**

실무 표준 구성을 따른다. 결과 형상:

| 서브넷 | 들어가는 것 |
| --- | --- |
| **퍼블릭** | **Nginx 태스크만** (외부에서 접근하는 유일한 지점) |
| **프라이빗** | 앱 태스크 ×2, RDS, Redis 태스크 |

앱이 외부(TMDB, 카카오/구글 OAuth)를 호출하고 ECR에서 이미지를 당겨오는 경로가 NAT Gateway다.

**에이전트가 (a) 퍼블릭 서브넷을 추천했던 이유와, 그 우려가 어디로 갔는지**

추천 근거는 **NAT Gateway가 "올렸다 내린다" 모델에서 가장 조용한 비용 폭탄**이라는 것이었다 — 시간당 과금(월 $30 남짓)에 데이터 처리 요금이 붙고, **ECS 태스크를 내려도 NAT은 그대로 남는다.** 콘솔에서 눈에 잘 띄지 않아 한 달 뒤 청구서로 알게 된다.

(b)를 선택했으므로 **그 위험이 사라진 것이 아니라 Q6으로 옮겨갔다.** 아래 teardown 워크플로가 이 지도에서 가장 실용적으로 중요한 항목이 됐다.

### Q2. RDS는 스냅샷 후 삭제, 검증할 때 복원 — **에이전트 추천 / 사용자 승인**

스냅샷은 백업 스토리지 요금이라 매우 싸고 **데이터가 그대로 보존**되며, 복원을 워크플로에 넣어 자동화할 수 있다.

- **RDS 유지**(월 $12~15)는 "검증할 때만 올린다"와 어긋난다.
- **매번 새로 만들고 배치로 채우기**는 콘텐츠는 되살아나지만 **사용자 계정·리뷰·플레이리스트가 날아간다** — 손으로 만든 데이터라 복구 방법이 없다.
- **postgres 컨테이너 + EFS**는 설정이 복잡한데 배우는 것이 RDS보다 적다.

복원에 10~20분이 걸리는 것이 대가인데, 검증 세션은 어차피 반나절짜리라 감당된다.

### Q3. Redis는 ECS 태스크로 (ElastiCache 아님) — **에이전트 추천 / 사용자 승인**

**Redis에 담기는 것은 시청 세션과 무효화 목록뿐이고 둘 다 잃어도 되는 데이터다.** 영속성·백업·페일오버가 필요 없는데 관리형을 쓸 이유가 없고, ElastiCache는 상시 과금이다.

`info.md`가 ElastiCache를 명시하지만 그것은 **상시 운영을 전제한 심화 항목**이다. 우리 목적지는 "검증할 때만 올린다"이므로 전제 자체가 다르다. **요구사항에서 의도적으로 벗어난 지점이므로 기록해 둔다.**

### Q4. Nginx를 ECS 서비스로, ALB 없음 — **에이전트 추천 / 사용자 승인**

`info.md`가 **Nginx 리버스 프록시**를 명시하므로 요구사항과 맞고, ALB의 시간당 과금(월 $16~20)도 피한다. Nginx 태스크가 퍼블릭 서브넷에서 앞에 선다.

앱은 **desired count 2인 ECS 서비스**로 두고 Nginx가 **Service Connect(또는 Cloud Map)** 로 찾는다. 이러면 `info.md`의 "ECS 인스턴스 2개 이상"을 실제로 만족한다.

**앱 컨테이너 여러 개를 한 태스크에 몰아넣지 않는다** — 편하지만 같은 호스트라 **분산의 절반만 검증된다.**

Nginx 설정에는 [실시간 WebSocket 아키텍처 설계]와 [로컬 개발·분산 환경 구성]이 넘긴 두 항목이 반드시 들어간다: **SSE 버퍼링 끄기**, **SockJS 폴백 트랜스포트 통과**.

### Q5. Kafka는 원칙만 정하고 구체 선택은 10주차로 미룬다 — **에이전트 추천 / 사용자 승인**

**원칙: 무료 티어가 있으면 그것, 없으면 ECS 태스크.**

Kafka는 **10주차 전환 항목**이라 4주차·7주차 배포에 필요 없다. 그리고 **관리형 서비스의 무료 티어 조건은 자주 바뀌므로**, 지금 확정하면 5개월 뒤에 맞지 않을 가능성이 높다. 그때 확인하는 것이 맞다.

### Q6. 이미지 태그는 커밋 SHA, **teardown도 워크플로로** — **에이전트 추천 / 사용자 승인**

**태그는 커밋 SHA. `latest`는 쓰지 않는다** — 무엇이 떠 있는지 추적할 수 없고 롤백이 불가능해진다.

**내리는 것도 `workflow_dispatch` 워크플로로 만든다.** Q1에서 (b)를 선택했으므로 **이 항목이 이 지도에서 가장 실용적으로 중요해졌다.** 콘솔에서 손으로 내리면 반드시 뭔가를 빠뜨리는데, 프라이빗 서브넷 구성에서 빠뜨리기 가장 쉬운 것이 정확히 **NAT Gateway**다.

**teardown 워크플로가 반드시 지워야 하는 것** (순서대로):

1. ECS 서비스 (앱 ×2, Nginx, Redis)
2. **NAT Gateway** ← 가장 비싸고 가장 잊기 쉽다
3. NAT에 붙은 **Elastic IP 해제**
4. RDS — **스냅샷을 먼저 만들고** 인스턴스 삭제
5. 남은 ENI·보안 그룹

**AWS Budgets 알림을 낮은 금액($10)으로 걸어 둔다.** 잊고 올려둔 것을 알아채는 마지막 그물이다.
