# AWS 배포 형상 확정

Type: grilling
Status: open

## Question

[12주 마일스톤 구획]이 이 항목을 안개에서 졸업시켰다. **4주차 1차 배포(단일 인스턴스) 전에 필요하다.**

지도의 제약을 다시 확인하고 시작한다 — **AWS는 검증할 때만 올리고 내린다**(상시 과금 회피). 따라서 **"내렸다 올려도 보존되어야 하는 상태가 무엇인가"** 가 이 티켓의 중심 질문이다.

- **무엇이 휘발되어도 되는가** — [분산 전환 이음매 확정]에 따라 시청 세션은 Redis에 있어 사라진다(허용 가능한가?). 알림·DM·사용자·콘텐츠는 DB라 남아야 한다.
- **DB를 어떻게 할 것인가** — RDS를 상시 띄우면 그 자체로 과금이다. 내렸다 올릴 때 데이터를 어떻게 유지하는가? 스냅샷? 아니면 배포 검증 때마다 배치로 다시 채우는가(백필 25분)?
- **1차 배포(단일)의 최소 형상** — ECS 서비스 1개 + DB + Redis. 로드밸런서가 필요한가, 퍼블릭 IP로 충분한가?
- **2차 배포(분산)의 형상** — Nginx 리버스 프록시를 ECS 태스크로 둘 것인가 ALB로 대체할 것인가. `info.md`는 **Nginx**를 명시한다.
- **Kafka·Redis를 관리형(Confluent Cloud, ElastiCache)으로 쓸 것인가**, ECS 태스크로 띄울 것인가. 관리형은 과금이 상시다.
- **이미지 저장소**(ECR)와 태그 전략.
- **비용 상한을 어떻게 지킬 것인가** — 예산 알림, 내리는 것을 잊었을 때의 안전장치.

[브랜치 전략과 CI/CD 결정]에서 **배포는 `workflow_dispatch` 수동 트리거, 자격증명은 OIDC**로 이미 정해졌다. 이 티켓은 **무엇을 향해 배포하는가**를 정한다.
