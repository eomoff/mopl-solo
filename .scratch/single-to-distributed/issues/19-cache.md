# 캐시 전략 확정

Type: grilling
Status: resolved
Blocked by: 04, 05

## Question

[분산 전환 이음매 확정]이 캐시를 **8번 이음매**로 두고 "(ㄴ) Spring Cache 추상화 뒤, 되돌리는 비용 가장 낮음(설정 수준)"까지만 정한 뒤, **캐시 대상은 도메인 모델이 정해져야 물을 수 있다**며 안개로 남겼다. [도메인 모델 확정]이 닫혔으므로 이제 물을 수 있다.

그 티켓이 남긴 단서 하나가 이 티켓의 중심에 있다 — **Redis가 1일차 의존성이므로 단일 단계에서도 로컬 캐시 대신 Redis를 바로 쓸 수 있다.** 그렇게 하면 시청 세션과 똑같이 **이 이음매에서는 전환을 겪지 않는다.**

- **Q1. 이번 지도에서 캐시를 실제로 도입하는가.** 도입하지 않고 "8번 이음매는 열어만 두고 비워 둔다"도 유효한 답이다. [도메인 모델 확정]이 정렬 축 계산 필드(`averageRating`·`reviewCount`·`watcherCount`·`subscriberCount`)를 **이미 DB 비정규화 컬럼으로 저장**하기로 했으므로, 목록 조회의 무거운 집계는 이미 사라졌다. 그렇다면 캐시가 지금 무엇을 벌어주는가.
- **Q2. 캐시 대상은 무엇인가.** 후보:
  - **사용자 인가 정보(`locked`·`role`)** — [분산 전환 이음매 확정] Q5가 "매 요청 DB 조회가 부담이면 캐시를 얹는다"고 단서를 달아둔 항목. [인증·인가와 토큰 무효화 설계]는 무효화 목록을 Redis에 뒀지만 `locked`·`role`의 소스 오브 트루스는 DB로 남겼다.
  - **콘텐츠 단건·목록** — 목록은 커서 페이지네이션 + 다중 정렬축이라 키 폭발이 나기 쉽다.
  - **외부 API 응답**(TMDB·SportsDB) — 배치가 이미 DB에 적재하므로 중복일 수 있다.
  - **태그 목록처럼 거의 변하지 않는 참조 데이터.**
- **Q3. 단일 단계의 구현체를 로컬(Caffeine)로 둘 것인가, 처음부터 Redis로 갈 것인가.** 이 선택이 곧 **이 이음매에서 전환을 겪을지**를 결정한다. 로컬로 시작하면 인스턴스 2대에서 캐시가 어긋나는 것을 눈으로 보게 되고(이 연습의 주제), Redis로 시작하면 그 체험이 없어진다. [분산 전환 이음매 확정]은 이음매를 전부 분산 구현으로 덮으면 단일 단계가 사라진다고 경고했다.
- **Q4. 무효화는 쓰기 시점 evict인가 TTL인가.** 계산 필드는 리뷰·구독·시청 세션이 바뀔 때마다 흔들린다. 캐시에 넣는 순간 **계약이 required로 요구하는 값이 틀린 값으로 나갈 수 있다.**
- **Q5. 캐시 미스가 아니라 캐시 스탬피드를 다룰 것인가.** 다루지 않기로 하는 것도 답이다.

판단 기준은 이 지도의 다른 결정과 같다 — **단일→분산 전환이라는 주제에 기여하는가.** 성능이 아니다. 개인 연습 규모에서 캐시가 성능으로 정당화될 일은 없다.

## Answer

### 결정

| | 결정 |
| --- | --- |
| Q1. 이음매 처리 | **(ㄷ) 인메모리로 시작해 10주차에 Redis로 전환한다** |
| Q2. 캐시에 담는 것 | `watcherCount`를 **뺀** 나머지. evict 트리거는 리뷰 CUD와 콘텐츠 수정 둘뿐 |
| Q3. 캐시 대상 경로 | **콘텐츠 단건 조회만.** 목록·플레이리스트는 캐시하지 않는다 |
| Q4. TTL | **두지 않는다.** evict만으로 간다 |
| Q5. 캐시 값 타입 | **캐시 전용 값 타입**을 따로 둔다 |
| Q6. evict 위치 | **평점 재계산 지점에 `@CacheEvict`.** 도메인 이벤트에 태우지 않는다 |
| Q7. 도입 시점 | **3주차** |

### 캐시는 성능이 아니라 이음매로 남는다

이 티켓에 들어올 때 캐시의 존재 이유가 흔들렸다. [도메인 모델 확정]이 정렬 축 계산 필드를 전부 DB 비정규화 컬럼으로 저장하기로 하면서 **목록 조회의 무거운 집계가 이미 사라졌고**, 개인 연습 규모에서 캐시가 성능으로 정당화될 일은 없다. 그래서 "접는다"도 실제 선택지였다.

남긴 근거는 성능이 아니라 **깨짐이 눈에 보인다**는 것이다. 인스턴스 2대에 Nginx가 라운드로빈으로 물리면 인메모리 캐시에 담긴 평점이 서버마다 갈리고, 브라우저에서 새로고침할 때마다 값이 튄다. 이 지도에서 **브라우저로 확인되는 깨짐은 드물고**, 고치는 비용은 설정 수준이다.

그 대가도 기록해 둔다 — **성능상 필요 없는 것을 학습 장치로 넣은 인위적인 선택이다.** 실무라면 고민 없이 처음부터 Redis다.

### `watcherCount`가 캐시 설계를 정했다

계약의 `ContentDto`는 required에 `watcherCount`를 박아뒀는데, 이 값은 시청 세션 JOIN/LEAVE마다 바뀐다. **DTO를 통째로 담으면 evict가 실시간으로 터져 히트율이 0에 수렴한다.**

그래서 캐시 값에서 `watcherCount`만 빼고, 응답 조립 시점에 따로 붙인다. 남은 evict 트리거는 **리뷰 생성·수정·삭제**와 관리자의 콘텐츠 수정 둘뿐이다.

이 선택이 데모까지 결정했다. 리뷰는 **사용자가 브라우저에서 직접 만드는 이벤트**이므로, 10주차에 리뷰 하나 달고 새로고침을 반복하면 평점이 튀는 것이 그대로 보인다. 정적 필드만 캐시했다면 evict가 관리자 행위에만 걸려 깨짐을 재현하는 데 관리자 로그인이 필요했을 것이다.

`PlaylistDto`는 `subscribedByMe`가 조회자마다 달라 **애초에 통째 캐시가 불가능**하다. 후보에서 빠진다.

### 캐시 값 타입을 따로 두는 이유

`ContentDto`를 담되 `watcherCount`를 비워두는 방식은 **`watcherCount`가 0인 `ContentDto`를 캐시 안에 실재하게 만든다.** 조립을 한 군데서만 빠뜨리면 그대로 응답으로 나가고, required 필드이므로 프론트가 0을 그린다. 타입으로 갈라두면 컴파일러가 막는다.

도메인 용어가 아니라 구현 타입이므로 `CONTEXT.md`에는 넣지 않는다.

### TTL을 두지 않는 이유

`ConcurrentMapCacheManager`에는 TTL이 없고 Redis에는 있다. TTL을 쓰면 **인메모리 모드에서만 값이 안 죽어** 두 모드가 비대칭이 되고, 10주차에 테스트가 뒤집힐 때 원인이 "전파 안 됨"인지 "TTL이 달라서"인지 흐려진다. evict 지점이 둘뿐이라 놓칠 여지도 좁다. 안전망이 필요해지면 Redis로 간 뒤에 붙인다.

### evict를 도메인 이벤트에 태우지 않는 이유

[알림·이벤트 파이프라인 설계]가 만든 `DomainEventPublisher` + `AFTER_COMMIT`에 태우는 쪽이 애그리거트 경계상 깔끔해 보이지만, **이벤트 발행도 10주차에 Kafka로 가는 별개의 이음매다.** evict를 거기 태우면 10주차에 두 이음매가 동시에 움직이고, 캐시가 안 지워질 때 원인이 캐시인지 이벤트 전달인지 분간이 안 된다. [로컬 개발·분산 환경 구성]이 프로파일을 거부하고 축별 프로퍼티로 간 것과 같은 이유다.

`averageRating`이 DB 비정규화 컬럼이라 리뷰 CUD는 이미 콘텐츠 쪽 갱신을 호출한다. 그 자리에 애너테이션 한 줄이면 되고, 콘텐츠 캐시를 지우는 코드가 콘텐츠 쪽에 있으므로 경계도 넘지 않는다.

### 3주차에 넣어 6주차부터 깨진 채로 지낸다

캐시가 붙을 조회 경로가 3주차에 생긴다. 그리고 **6주차에 인스턴스가 2대로 서는 순간부터 캐시는 실제로 깨진 채로 4주를 지낸다.** 이것이 의도다 — 10주차 전환이 "숙제"가 아니라 "4주 동안 눈에 거슬리던 것을 고치는 일"이 된다.

6·7주차에 브라우저에서 평점이 튀는 것을 보고도 두는 것이 **버그가 아니라 예정된 상태**라는 사실은, [이음매를 감싸는 테스트 전략]의 통과하는 테스트가 문서 역할로 붙든다.

### 규약에서 도출된 것 (결정이 아님)

- 캐시 이름 `content`, 키는 콘텐츠 UUID
- 스위치는 `mopl.cache.mode: local | redis` — [로컬 개발·분산 환경 구성]의 `mopl.<축>.mode` 규약
- Redis 직렬화는 JSON. `Instant` 때문에 `JavaTimeModule`이 필요하다. **인메모리는 객체를 그대로 담으므로 이 문제는 10주차 전환 시점에 처음 터진다**
- 이음매 테스트는 같은 JVM에 컨텍스트 2개를 띄워 *"인메모리 모드에서는 한쪽 evict가 다른 쪽에 전파되지 않는다"* 가 **통과하는** 형태. `ConcurrentMapCacheManager`는 인스턴스별로 생기므로 [이음매를 감싸는 테스트 전략]이 경고한 "단일 구현이 `static`이면 거짓 통과" 함정에는 걸리지 않는다
- 전환은 [브랜치 전략과 CI/CD 결정]대로 10주차 PR 하나

### 이 티켓이 닫은 다른 단서

[분산 전환 이음매 확정]이 8번 이음매에 달아둔 "단일 단계에서 로컬 캐시로 갈지 Redis로 바로 갈지는 캐시 대상이 정해질 때 함께 정한다(안개 항목)"가 여기서 닫혔다. **로컬로 간다.**

같은 티켓 Q5의 "매 요청 DB 조회가 부담이면 캐시를 얹는다"는 단서는 이 티켓의 대상이 아니다 — [인증·인가와 토큰 무효화 설계]가 이미 실행해서 닫았고, 매 요청 조회는 Redis 무효화 목록 1회이지 DB 조회가 아니다.

### 다른 티켓에 미치는 영향

[12주 마일스톤 구획]의 주차표에 **캐시 도입 주차가 비어 있었다**(10주차 "캐시→Redis" 전환만 있었다). 3주차에 도입을 추가한다. 해당 티켓에 보충을 단다.

### 결정 주체

Q1~Q7 모두 에이전트가 추천하고 사용자가 승인했다. Q1에서 "ㄷ로 가자", 이후 "둘 다 추천대로", "셋 다 추천대로", "3주차로 가자".
