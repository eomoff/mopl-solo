# 로깅 정책 확정

Type: grilling
Status: resolved
Blocked by: 08, 09, 17

## Question

무엇을 어느 수준으로 남길 것인가. 지도 곳곳에서 조각조각 정해졌을 뿐 정책으로 모인 적이 없다.

**이미 정해진 것**

- [콘텐츠 수집 배치 설계] — 배치 메트릭 4종 확정.
- [알림·이벤트 파이프라인 설계] — **`ERROR` level은 쓰지 않는다.**
- [예외·에러 응답 계약 확정] — **프론트가 서버 `message`를 한 번도 표시하지 않으므로** `message`·`details`는 개발자용으로 최적화한다. 그 개발자가 그것을 **어디서** 읽는가는 열려 있다.

**열린 질문**

- **Q1. 인스턴스가 2대가 되면 로그는 두 곳으로 흩어진다.** 한 요청이 어느 인스턴스에서 처리됐는지, 한 사용자의 WebSocket 연결과 그 알림이 서로 다른 인스턴스에 있을 때 둘을 어떻게 잇는지. **상관관계 ID(MDC)를 넣을 것인가, 넣는다면 언제 넣는가** — 처음부터인가 전환 시점인가. 이 질문은 이 노력의 주제와 정면으로 닿는다.
- **Q2. 로그 포맷.** 평문인가 JSON인가. 분산 전 단계에서 JSON은 읽기 불편하고, 분산 후 평문은 집계가 안 된다. [로컬 개발·분산 환경 구성]이 만든 `mopl.<축>.mode` 프로퍼티처럼 **포맷도 설정으로 가를 것인가.**
- **Q3. 어디에 남기는가.** 로컬은 콘솔이면 된다. AWS에서는 — [AWS 배포 형상 확정]이 ECS 태스크로 갔으므로 CloudWatch Logs가 기본값이 되는데, **검증할 때만 올리고 내리는** 형상에서 로그 보존은 무슨 의미인가.
- **Q4. 요청 로그를 남기는가.** 남긴다면 무엇을(경로·상태코드·소요시간·사용자) 어느 수준으로. 스프링 기본 로그로 충분한가.
- **Q5. 마스킹.** 비밀번호·JWT·리프레시 토큰·이메일이 로그에 새지 않게 하는 규칙. 저장소가 **public**이고 CI 로그도 공개된다.
- **Q6. `ERROR`를 쓰지 않기로 한 규칙이 전역인가.** [알림·이벤트 파이프라인 설계]의 결정이 알림 파이프라인 한정인지, 애플리케이션 전체 규약인지. 전체라면 **진짜 장애를 무엇으로 표시하는가.**

## Answer

### 결정

| | 결정 |
| --- | --- |
| Q1. 상관관계 ID | **직접 만든 MDC 필터.** `X-Request-ID`가 있으면 이어받고 없으면 생성 |
| Q2. 포맷 | **로컬 평문 / 배포 JSON** (Boot structured logging) |
| Q3. 요청 로그 | **남긴다.** 본문·헤더 없이, 정적 리소스와 actuator 제외 |
| Q4. 마스킹 | **"애초에 안 찍는다" 규율.** 마스킹 필터는 만들지 않는다 |
| Q5. 위치·보존 | **stdout만.** 보존 기간 명시(7일), teardown에 로그 그룹 삭제 |
| Q6. 레벨 기준 | **"사람이 개입해야 하는가".** 4xx는 `ERROR`가 아니다 |
| Q7. 예외 로깅 | **`@RestControllerAdvice` 한 곳에서만.** 스택트레이스는 5xx에만 |
| Q8. WS·SSE | 연결·해제 `INFO`, 메시지 `DEBUG`. **로그에 인스턴스 식별자를 고정 필드로** |

### 이 티켓이 달고 있던 질문 하나가 오독이었다

이 티켓을 만들 때 넣은 Q6 *"`ERROR` level을 쓰지 않기로 한 규칙이 전역인가"* 는 **[알림·이벤트 파이프라인 설계]의 결정을 잘못 읽은 것이었다.** 그 결정은 로그 레벨이 아니라 **계약의 `NotificationDto.level` 필드**(`INFO`/`WARNING`/`ERROR`)에 대한 것이다 — 사용자에게 보이는 알림 표시 수준이고, *"프론트는 `level`로 아이콘과 배경색만 가른다"* 가 그 증거다. 계약에서 확인했다. 로깅과 무관하므로 버렸다.

### 상관관계 ID — 도구를 들이지 않고 손으로 만든다

처음에 **"손으로 만든 MDC 필터는 표준이 아니다"** 라고 했으나 **과한 말이었다.** 실무의 요청 추적 ID 구현은 셋으로 갈리고 셋 다 현업에서 쓴다 — APM 에이전트(한국 실무에서 가장 흔하다), Micrometer Tracing + OTel(새 Spring 프로젝트의 표준 경로), 직접 만든 MDC 필터(애플리케이션이 하나면 여전히 흔하다). 트레이싱의 가치는 **서비스가 여러 개일 때** 커지는 것이고, 이 프로젝트는 애플리케이션 하나에 인스턴스 2대다.

**형태는 엣지에서 받는 쪽으로 간다.** 앱이 ID를 자체 발급하는 것보다, 앞단이 준 것을 이어받는 것이 실무에서 더 흔하다. 7주차에 Nginx가 서면 `X-Request-ID`가 엣지 액세스 로그와 앱 로그를 같은 ID로 잇는다. 헤더가 있으면 이어받고 없으면 새로 만든다.

**대가는 비동기 경계 다섯 곳이다.** MDC는 `ThreadLocal` 기반이라 스레드가 바뀌면 사라진다.

| 경계 | 주차 | 필요한 것 |
| --- | --- | --- |
| Spring Batch | 3주차 | 리스너 |
| WebSocket 메시지 처리 | 5주차 | `ChannelInterceptor` |
| `@Async` 이벤트 리스너 | 9주차 | `TaskDecorator` |
| SSE | 9주차 | 커넥션별 처리 |
| Kafka 컨슈머 | 10주차 | 헤더 전파 |

**각 기능이 생기는 주차에 하나씩 붙인다.** 다섯을 한 번에 하지 않으면 부담이 흩어진다.

정직하게 기록해 둔다 — 이 학습은 **이 지도의 주제와 다른 축이다.** 캐시는 인스턴스가 2대가 되는 순간 깨지는 단일→분산의 정확한 예시였지만, MDC 전파가 끊기는 것은 **인스턴스가 1대여도 생기는 문제**다. Micrometer Tracing을 골랐다면 다섯 곳이 자동으로 처리됐을 것이고, 그것도 합리적인 선택이었다.

### 4xx를 `ERROR`로 남기지 않는다

레벨 기준은 **"사람이 개입해야 하는가"** 다.

| 레벨 | 기준 | 예 |
| --- | --- | --- |
| `ERROR` | 사람이 개입해야 한다 | 재시도 후에도 실패한 배치, 예상 못한 예외(5xx) |
| `WARN` | 자동 복구됐으나 반복되면 문제 | TMDB 429 후 재시도 성공, 로그인 실패, 리프레시 토큰 재사용 감지 |
| `INFO` | 상태 변화의 이정표 | 기동, 배치 Job 시작·종료, 어드민 초기화, 마이그레이션 적용 |
| `DEBUG` | 로컬에서만 | 쿼리, 페이로드 |

**4xx가 핵심이다.** [예외·에러 응답 계약 확정]이 계약을 따라 **중복 가입도 400, 404 미선언 경로의 없는 리소스도 400**으로 내보내기로 했다. 이것을 `ERROR`로 세면 **정상적인 사용자 실수가 오류 지표를 덮는다.** 클라이언트 잘못은 서버 오류가 아니다.

### 예외는 한 곳에서, 스택트레이스는 5xx에만

발생 지점에서 로깅하고 다시 던지면 **같은 예외가 두세 번 찍힌다.** 잡아서 처리하거나, 던지고 핸들러에 맡기거나 둘 중 하나다. 4xx에 스택트레이스를 찍으면 정상적인 검증 실패 하나가 로그 스무 줄이 된다.

[예외·에러 응답 계약 확정]이 *"프론트가 서버 `message`를 한 번도 표시하지 않으므로 `message`·`details`는 개발자용으로 최적화한다"* 고 했는데, **그 개발자가 실제로 읽는 곳이 이 로그다.** 응답 본문과 로그가 같은 내용을 담는다.

`CLAUDE.md`가 이미 `e.printStackTrace()`를 금지하고 `@Slf4j`를 요구하므로 결이 맞는다.

### 로그가 전환의 증거가 된다

WebSocket·SSE 연결·해제를 `INFO`로 남긴다. 일반적인 실무 표준은 `DEBUG`이지만, **이 프로젝트에서는 연결이 어느 인스턴스에 붙었는지가 6주차 전환 검증의 핵심**이다. [분산 전환 이음매 확정]이 하나로 통합한 "전파 이음매"가 정확히 이 문제이고, 로그가 그 증거다.

그래서 **인스턴스 식별자를 로그의 고정 필드로 넣는다.** 인스턴스가 2대가 되면 `traceId`만으로는 부족하고, "어느 인스턴스가 처리했나"가 있어야 채팅이 반쪽만 보이는 이유를 쫓을 수 있다. 호스트명이나 컨테이너 ID를 쓴다.

### 마스킹 — 이미 켜져 있던 것

저장소가 public이라 방어를 세 겹으로 제안했으나, **2차는 이미 켜져 있었다.**

```
secret_scanning:                 enabled
secret_scanning_push_protection: enabled
```

GitHub이 public 저장소에 기본으로 켜준다. gitleaks 같은 것을 CI에 더 넣는 것은 보안에 민감한 조직에서 하는 일이고 개인 프로젝트에는 과하다. **없는 할 일을 만들 뻔했다.**

남는 것은 1차 규율뿐이다 — **요청 본문과 헤더를 로그에 넣지 않는다.** 마스킹 필터는 놓친 패턴이 하나라도 있으면 뚫리므로 만들지 않는다. `Authorization` 헤더도 마찬가지다.

### 규약에서 도출된 것 (결정이 아님)

- CloudWatch 보존 기간 **7일**. Never expire는 알려진 비용 함정이고, [AWS 배포 형상 확정]이 상시 과금을 피하려고 만든 형상과 어긋난다
- 로그 패턴에 `traceId` + 인스턴스 식별자
- `actuator`의 `http.server.requests`가 지연·상태코드 집계를 담당하므로 **요청 로그는 건별 추적용**이다. 7주차에 Nginx가 서면 엣지 액세스 로그가 추가된다
- 배치 메트릭 4종(처리·실패 건수, 소요 시간, 마지막 성공 시각)은 [콘텐츠 수집 배치 설계]에서 이미 확정됐다
- 파일 로깅은 하지 않는다 — 컨테이너에서 태스크가 죽으면 파일도 사라진다 (12-factor)

### 다른 티켓에 미치는 영향

- **[12주 마일스톤 구획]** — 1주차에 MDC 필터와 로그 설정이 추가된다. 비동기 전파는 각 기능 주차에 붙는다.
- **[AWS 배포 형상 확정]** — teardown 워크플로에 **로그 그룹 삭제**가 추가된다. 그 티켓이 *"손으로 내리면 NAT Gateway를 빠뜨린다"* 고 경고했는데, 로그 그룹도 같은 종류의 누락이다.

### 새 안개 — Actuator 노출 범위

[콘텐츠 수집 배치 설계]가 **커스텀 메트릭 4종을 Actuator로 노출**하기로 했으나 **누가 볼 수 있는지가 지도 어디에도 없다.** ECS와 Nginx가 헬스체크를 하려면 `/actuator/health`가 인증 없이 열려야 하는데, `/actuator/metrics`가 함께 열리면 public 인터넷에 내부 지표가 노출된다. [인증·인가와 토큰 무효화 설계]가 SecurityFilterChain을 설계했으나 actuator 경로는 다루지 않았다.

로깅과 인접하지만 **관측·인가라는 다른 축**이므로 이 티켓에서 흡수하지 않고 안개로 올린다.

### 결정 주체

Q2·Q3·Q5는 사용자가 **"전부 실무 현업 표준으로"** 라고 지시했고 에이전트의 추천이 표준과 일치했다. Q6·Q7·Q8은 추천대로 승인했다.

**Q1은 두 번 정정을 거쳤다.** 에이전트가 "손으로 만든 MDC 필터는 표준이 아니다"라고 과장했고, 사용자가 *"ㄱ이 실무 현업에서 많이 사용하는거야? 학습용으로서 매우 좋아?"* 로 되물어 그 과장이 드러났다. 실제로는 세 방식이 모두 현업에서 쓰이며, 학습 가치도 "매우 좋다"기보다 **"배울 것은 실하지만 이 지도의 주제와 다른 축이고 손이 다섯 번 간다"** 가 정확하다. 그 정정 위에서 (ㄱ)으로 승인했다.

**Q4도 정정됐다.** 에이전트가 GitHub Secret Scanning 활성화를 할 일로 제시했으나 확인해보니 이미 켜져 있었다.
