# 어드민 계정 초기화 규칙

Type: grilling
Status: resolved
Blocked by: 06

## Question

`docs/info.md`가 요구한다 — **"초기화: 서버 시작 시 어드민 계정을 자동으로 초기화합니다."** 한 줄뿐이고 나머지는 전부 열려 있다.

[인증·인가와 토큰 무효화 설계]가 인증의 나머지를 모두 닫았지만(리프레시 토큰 저장·회전, Redis 무효화 목록, 임시 비밀번호를 사용자 행에, 탈퇴 미구현) **최초의 어드민이 어떻게 존재하게 되는가**는 다루지 않았다. 계약에 어드민 전용 경로가 없어 **인가가 경로가 아니라 메서드 수준에서 갈리므로**, 어드민이 하나도 없으면 권한 변경·계정 잠금·콘텐츠 등록 경로 전체가 아무도 통과할 수 없는 상태가 된다.

- **Q1. 자격 증명은 어디서 오는가.** 저장소가 **public**이라 비밀번호를 코드나 `application.yml`에 둘 수 없다. [로컬 개발·분산 환경 구성]이 `.gitignore`에 `.env`를 추가해 뒀다. 그러면 AWS에서는 — [AWS 배포 형상 확정]이 **장기 키를 시크릿에 넣지 않는다**는 원칙으로 OIDC를 택했는데, 어드민 비밀번호는 어떤 경로로 들어가는가.
- **Q2. 멱등성.** 이미 있으면 무엇을 하는가. 건너뛰는가, 비밀번호를 매 시작마다 설정값으로 되돌리는가(운영에선 위험, 연습에선 편리), 아니면 없을 때만 만드는가.
- **Q3. 인스턴스가 2대면 초기화도 2번 돈다.** [분산 전환 이음매 확정]이 **배치 중복 실행**을 7번 이음매로 잡아 "(ㄷ) 전환 시점에 잠금 추가"로 미뤘는데, 어드민 초기화도 같은 모양의 문제다. **같은 이음매로 묶을 것인가, 이메일 unique 제약이 잡아주는 것으로 충분하다고 볼 것인가.** 후자라면 두 번째 인스턴스가 받을 제약 위반 예외를 정상 경로로 삼켜야 한다.
- **Q4. 어디서 실행하는가.** `ApplicationRunner` / `ApplicationReadyEvent` / DB 마이그레이션(Flyway) 중 무엇인가. 마이그레이션이면 Q3이 통째로 사라지지만 비밀번호 해시를 SQL에 박아야 한다.
- **Q5. 검증 형상과의 충돌.** [AWS 배포 형상 확정]은 RDS를 **스냅샷 후 삭제·복원**한다. 복원된 DB에는 어드민이 이미 있다. Q2의 답이 이 시나리오에서도 성립하는지 확인한다.

## Answer

### 결정

| | 결정 |
| --- | --- |
| Q1. 자격 증명 | 이메일·이름은 `application.yaml`, **비밀번호만 `MOPL_ADMIN_PASSWORD` 환경변수** |
| Q2. 멱등성 | **없을 때만 만든다.** 있으면 아무것도 안 한다 |
| Q3. 인스턴스 2대 경합 | `users(email)` unique 제약에 맡기고 제약 위반을 정상 경로로 삼킨다 |
| Q4. 실행 위치 | `ApplicationRunner`가 호출, 로직은 Service. **Flyway를 들이지 않는다** |
| Q5. 어드민 소멸 방지 | **자기 자신의 `role`·`locked` 변경 금지 → 403** |
| Q6. 이메일 선점 | **무시한다.** "있으면 승격"은 배제 |
| Q7. 환경변수 부재 | **기동 실패.** `.env.example`에 로컬용 값을 둔다 |

### 어드민 이메일은 비밀이 아니라 설정이다

[로컬 개발·분산 환경 구성] Q6이 "비밀은 전부 환경변수"로 정했지만, **어드민 이메일과 이름은 비밀이 아니다.** 저장소에 보여도 문제가 없고 오히려 보여야 한다. 비밀번호만 `MOPL_ADMIN_PASSWORD`로 빼서 DB 비밀번호·JWT 서명 키와 같은 경로에 합류시킨다.

AWS에서 이 환경변수를 무엇으로 채우는지는 **이 티켓이 여는 문제가 아니다.** DB 비밀번호와 JWT 서명 키가 이미 같은 처지이고, [AWS 배포 형상 확정]이 그것을 정하지 않은 채 닫혔다. 어드민 비밀번호를 그 대열에 세우는 것으로 족하다.

### 어드민 0명은 자기 자신 검사 하나로 구조적으로 불가능해진다

계약의 `PATCH /api/users/{userId}/role`과 `/locked`는 어드민만 호출한다. 유일한 어드민이 자기를 강등하거나 잠그면 **아무도 그 경로를 다시 못 쓴다.** Q2가 "없을 때만 만든다"이므로 재시작으로도 복구되지 않는다 — 계정은 존재하기 때문이다.

**요청자와 대상이 같으면 403**, 이 조건 하나로 끝난다.

- 어드민이 A 혼자 → A는 자기를 못 바꾼다 → 0명 불가
- 어드민이 A, B → A가 B를 강등 → A만 남고 A는 자기를 못 바꾼다 → 0명 불가

"마지막 어드민을 보호한다"는 대안은 더 강해 보이지만 **현재 어드민 수를 세는 쿼리와 경합**을 들여온다(두 어드민이 동시에 서로를 강등하면 둘 다 통과할 수 있다). 자기 자신 검사에는 경합이 없다 — 요청자가 곧 대상이다.

**어드민이 다른 유저를 승격시킬 수 있다는 것이 이 결정을 대신하지는 않는다.** 그 안전망은 두 번째 어드민을 이미 만들어둔 뒤에만 작동하는데, 초기 상태는 정확히 1명이다.

403인 이유: 권한 자체는 있고 그 동작이 금지된 상황이며, 계약이 두 경로에 403을 선언해뒀다.

### "있으면 ADMIN으로 승격"은 권한 상승 취약점이다

Q6의 선점 문제를 "이미 있으면 승격시킨다"로 풀면 **공격 방법을 만들어주게 된다.**

1. 공격자가 어드민 이메일로 그냥 회원가입한다(비밀번호는 자기가 정한다)
2. 서버가 재시작한다
3. 초기화가 "있는데 `USER`네" 하고 `ADMIN`으로 승격시킨다
4. 공격자가 자기 비밀번호로 로그인해 관리자가 된다

가입 한 번으로 관리자가 된다. 배제한다.

선점 자체는 **무시한다.** 근거는 "틈이 없다"가 아니라 **"틈이 무시할 만큼 좁다"** 이다 — `ApplicationRunner`가 웹 서버보다 늦게 돌 수 있어 첫 기동의 찰나에 정확히 그 이메일로 가입 요청이 들어오면 이론상 가능하지만, 그 시점에는 아직 아무도 서버 주소를 모른다. 개인 연습 프로젝트에서 방어할 시나리오가 아니다. 정상 상황에서 뒤늦은 가입 시도는 unique 제약에 걸려 [예외·에러 응답 계약 확정]대로 400이 나간다.

### 이것은 이음매가 아니다

[분산 전환 이음매 확정]이 **배치 중복 실행**을 7번 이음매로 두고 "전환 시점에 잠금 추가"로 미뤘고, 어드민 초기화도 겉모습이 같다. 하지만 **전환할 것이 없다.**

실제 INSERT가 일어나는 것은 첫 배포 딱 한 번이고, 그 뒤로는 Q2의 "없을 때만" 조건에서 걸러진다. 한 번뿐인 경합에 잠금 인프라를 끌어올 이유가 없다. 두 번째 인스턴스가 받는 제약 위반은 예외가 아니라 **정상 경로**로 삼킨다.

### Flyway를 들이지 않는다 — 그리고 스키마 관리가 안개로 드러났다

마이그레이션으로 어드민을 넣으면 Q3이 통째로 사라지지만 **BCrypt 해시를 SQL 파일에 박아 public 저장소에 커밋**하게 된다. 비밀번호를 환경변수로 뺀 Q1의 결정이 그 자리에서 무너진다.

더 근본적으로, **지도에 스키마 관리 도구가 없다.** Flyway·Liquibase가 `build.gradle`에도 어느 티켓에도 없다. 이 결정 하나를 위해 도구를 들이는 것은 배보다 배꼽이다.

**그 사실 자체가 지도의 구멍이다.** 이 티켓은 "어드민 초기화에 Flyway를 쓰지 않는다"까지만 답했고, 스키마를 `ddl-auto`로 관리할지 마이그레이션 도구를 들일지는 답하지 않았다. 맵의 안개로 올린다.

`CLAUDE.md`의 "`@Scheduled` 메서드에 직접 로직 금지 — Service 위임"과 같은 결로, Runner는 호출만 하고 로직은 Service에 둔다.

### 없으면 죽는다

`MOPL_ADMIN_PASSWORD`가 없을 때 경고만 남기고 기동하는 것은 **가장 나쁜 실패 방식이다.** 서버는 멀쩡히 떠 있고, 2주차에 어드민 로그인이 안 되는 것을 발견한 뒤에야 로그를 뒤지게 된다. 원인과 증상이 멀어진다. AWS 태스크 정의에서 빠뜨렸을 때도 "떴는데 어드민이 없는" 상태가 된다.

로컬 개발 불편은 이미 해결되어 있다 — [로컬 개발·분산 환경 구성]이 `.gitignore`에 `!.env.example` 예외를 남겨뒀다. **다만 파일 자체는 아직 없으므로 1주차에 만든다.**

프로파일로 동작을 가르는 대안은 [로컬 개발·분산 환경 구성]이 세운 "프로파일로 가르지 않는다" 원칙과 어긋난다.

### 규약에서 도출된 것 (결정이 아님)

- 비밀번호 해싱은 `PasswordEncoder`(BCrypt)
- 어드민 이름은 설정값, `profileImageUrl`은 null
- `role`은 계약의 enum 그대로 `ADMIN`
- 검증은 어드민으로 로그인해 다른 유저에게 권한을 줘보는 것으로 한다 — [12주 마일스톤 구획] 2주차 확인 지점에 얹으면 초기화·인증·인가가 한 번에 검증된다

### 다른 티켓에 미치는 영향

- **[도메인 모델 확정]** — unique 제약 목록에 `users(email)`이 **빠져 있다.** Q3이 정확히 그 제약에 기대므로 보충을 단다.
- **[12주 마일스톤 구획]** — 1주차에 `.env.example` 생성이 추가된다.

### 결정 주체

Q1~Q4는 에이전트가 추천하고 사용자가 일괄 승인했다("넷 다 추천대로 가자"). Q5는 사용자가 "어드민이 유저에게 권한 줄 수 있다"는 반론을 제기해 그 안전망이 **두 번째 어드민을 만들어둔 뒤에만 작동한다**는 점을 확인한 뒤 (ㄱ)으로 승인했다. Q6·Q7은 추천대로 승인했다.

## 보충 (2026-09-05, [스키마 관리 방식 확정] 해결 중)

**Q4의 근거 하나가 무효가 됐다. 결정은 그대로다.**

Flyway를 쓰지 않기로 한 근거는 둘이었다.

- ① BCrypt 해시를 SQL 파일에 박아 public 저장소에 커밋하게 된다 → **그대로 유효**
- ② 이 결정 하나를 위해 지도에 없는 도구를 들이는 것은 배보다 배꼽이다 → **무효.** [스키마 관리 방식 확정]이 Flyway를 1주차부터 도입하기로 했다

**어드민 초기화는 계속 `ApplicationRunner`다.** 근거 ①이 홀로 결정을 지탱한다 — 어드민 비밀번호는 환경변수로 주입하기로 했고([어드민 계정 초기화 규칙] Q1), 마이그레이션에 해시를 박으면 그 결정이 그 자리에서 무너진다.

덧붙여 **Q3의 경합 처리도 성격이 분명해졌다.** Flyway는 자체 DB 잠금으로 인스턴스 2대의 동시 마이그레이션을 직렬화하지만, 어드민 초기화는 그 잠금 밖에서 돈다. `users(email)` unique 제약에 맡긴다는 결정은 그대로다.
