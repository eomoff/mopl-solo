# 스키마 관리 방식 확정

Type: grilling
Status: resolved
Blocked by: 05, 15, 18, 21

## Question

**지도 어디에도 스키마를 무엇으로 관리하는지가 없다.** [어드민 계정 초기화 규칙]을 풀다 드러났다 — 그 티켓은 "어드민 초기화에 Flyway를 쓰지 않는다"까지만 답했고, 스키마 자체를 `ddl-auto`로 둘지 마이그레이션 도구를 들일지는 답하지 않았다. `build.gradle`에도 Flyway·Liquibase가 없다.

**사용자가 Flyway 도입 의향을 밝혔다(2026-09-05).** 따라서 이 티켓의 무게중심은 "쓸 것인가"가 아니라 **"어떻게 쓸 것인가"** 에 있다. 도구 선택 자체를 다시 열 여지는 남겨두되, 아래 질문들이 실제 내용이다.

### Q1. 1주차부터 마이그레이션인가, 스키마가 굳은 뒤 baseline인가

이 티켓의 중심 질문이다. [12주 마일스톤 구획]이 **세로로 얇게 뚫고 넓히는** 방식을 택했으므로 엔티티는 12주 내내 늘어난다. 1주차부터 마이그레이션을 쓰면 **설계가 가장 많이 흔들리는 시기에 필드 하나 고칠 때마다 파일이 하나씩 쌓인다.**

대안은 초기 몇 주를 `ddl-auto`로 놀다가 스키마가 굳는 시점에 baseline `V1`을 뜨는 것이다. 그러면 마찰은 줄지만 **그 전 기간의 스키마 변경 이력이 없다.**

판단 기준은 이 연습의 주제다 — 스키마 이력 관리가 **단일→분산 전환**에 기여하는가, 아니면 실무 감각을 얻는 별개의 학습인가.

### Q2. 테스트에서 Flyway를 돌리는가

[이음매를 감싸는 테스트 전략]이 **PostgreSQL을 Testcontainers로 진짜로 띄우기로** 했다. 컨테이너가 뜰 때마다 마이그레이션을 전부 재생하면 12주차쯤엔 느려진다.

`ddl-auto: create-drop`으로 대체하면 빠르지만 **"테스트가 검증한 스키마 ≠ 운영 스키마"** 가 된다. 마이그레이션에 오타가 있어도 테스트는 초록이다.

### Q3. `ddl-auto: validate`를 병행하는가

엔티티와 실제 스키마가 어긋나면 기동 시점에 잡아준다. Flyway를 쓰면서 `validate`를 켜는 것이 실무 관용형인데, 마이그레이션과 엔티티를 **두 곳에 같은 것을 쓰는 중복**이기도 하다.

### Q4. Spring Batch 메타데이터 테이블은 누가 만드는가

[도메인 모델 확정]이 **"Spring Batch 메타데이터 테이블은 서비스 DB에 함께 둔다"** 고 정했다. Boot의 `spring.batch.jdbc.initialize-schema`에 맡길 것인가, Flyway 마이그레이션으로 끌어올 것인가. 후자면 Spring Batch 버전이 올라갈 때 DDL을 직접 따라가야 한다.

### Q5. RDS 스냅샷 복원과 `flyway_schema_history`

[AWS 배포 형상 확정]이 **RDS를 스냅샷 후 삭제·복원**하기로 했다. 이력 테이블도 함께 복원되므로 정합성은 맞을 것으로 보이지만, **검증할 때만 올렸다 내리는** 형상에서 마이그레이션이 언제 도는지(배포마다? 첫 기동에만?) 확인이 필요하다.

### Q6. 되돌리기

[브랜치 전략과 CI/CD 결정]이 **이음매 전환마다 PR 하나 = 되돌릴 수 있는 단위**로 정했다. 그런데 Flyway Community에는 undo가 없다. 코드는 되돌려도 스키마는 안 되돌아간다. 이 비대칭을 어떻게 다룰 것인가 — 되돌리는 마이그레이션을 손으로 쓰는가, 아니면 "되돌리지 않고 앞으로만 간다"를 원칙으로 삼는가.

---

**이 티켓이 닫히면 손봐야 할 것**

- [어드민 계정 초기화 규칙] — Q4의 근거 ②("없는 도구를 이것 하나 위해 들이는 건 배보다 배꼽")가 **무효가 된다.** 근거 ①(비밀번호 해시를 SQL에 박아 public 저장소에 커밋하게 된다)은 그대로이므로 **결정 자체는 유지**된다. 보충을 단다.
- [도메인 모델 확정] — 정해둔 테이블과 unique 제약이 그대로 첫 마이그레이션의 내용이 된다.
- [12주 마일스톤 구획] — 1주차 세팅에 배선이 추가된다.

## Answer

### 결정

| | 결정 |
| --- | --- |
| Q1. 도입 시점 | **1주차부터 마이그레이션.** 4주차 첫 배포 전까지 파일 수정 허용, 그 뒤 append-only |
| Q2. 테스트 스키마 | **Flyway.** `ddl-auto: create-drop`으로 대체하지 않는다 |
| Q3. `validate` | **병행한다** |
| Q4. Spring Batch 메타 | **Flyway로 가져온다** |
| Q5. 되돌리기 | **forward-only.** 파괴적 변경은 두 단계로 나눈다 |
| Q6. `V1`의 범위 | **주차마다 필요한 것만** |

### 들어올 때의 전제 — 지금은 스키마가 아예 안 만들어진다

`application.yaml`에 `spring.application.name`밖에 없다. PostgreSQL은 임베디드가 아니므로 `ddl-auto`의 기본값이 `none`이고, **1주차에 첫 엔티티를 쓰는 순간 막힌다.** 이 티켓이 1주차 작업의 선행 조건이라는 뜻이다.

### 1주차부터 쓰되, 4주차 전까지는 고쳐 쓴다

"설계가 흔들리는 초기에 마이그레이션 파일이 쌓여 마찰이 된다"는 걱정은 **실제로는 생기지 않는다.** append-only 규율은 *배포된 뒤에* 필요한 것이고, [12주 마일스톤 구획]의 **첫 배포는 4주차**다. 그 전까지 DB는 언제든 날릴 수 있으므로 마이그레이션 파일을 그냥 고쳐 쓰면 되고, Testcontainers는 매번 새 DB라 애초에 문제가 없다.

따라서 규칙은 **"4주차 첫 배포 전까지는 마이그레이션 파일 수정 허용, 그 뒤로 append-only"** 다.

스키마가 굳은 뒤 baseline을 뜨는 방식은 **레거시 DB에 Flyway를 나중에 얹을 때** 쓰는 것이지 새 프로젝트에서 할 일이 아니다.

### 스키마도 인프라다

[이음매를 감싸는 테스트 전략]이 **"인프라는 진짜, 외부 API는 가짜"** 를 원칙으로 세웠다. 스키마는 인프라 쪽이다.

테스트를 `ddl-auto: create-drop`으로 돌리면 빠르지만 **마이그레이션에 오타가 있어도 CI가 초록이다** — 검증해야 할 바로 그것을 검증하지 않게 된다. 12주차에 마이그레이션이 서른 개여도 수백 ms 수준이고 컨텍스트 캐싱이 대부분 흡수한다.

`ddl-auto: validate`를 함께 켜는 것은 중복이 아니라 **교차 검증**이다. 마이그레이션에 컬럼을 빠뜨렸을 때 런타임 쿼리가 터지는 대신 부팅이 실패한다.

### 스키마 소유권을 한 곳에

[도메인 모델 확정]이 **Spring Batch 메타데이터 테이블을 서비스 DB에 함께 두기로** 했다. Boot의 `spring.batch.jdbc.initialize-schema`에 맡기면 **같은 DB의 스키마를 두 도구가 나눠 만들고**, Q3의 `validate`와 실행 순서가 얽힌다. 공식 DDL을 마이그레이션에 복사해 Flyway가 전부 소유한다. Spring Batch DDL을 따라가야 하는 부담은 있으나 12주 안에 Boot 버전을 올릴 일이 없다.

### forward-only와 두 단계 삭제

[브랜치 전략과 CI/CD 결정]이 "이음매 전환마다 PR 하나 = 되돌릴 수 있는 단위"로 정했는데, **스키마는 그 규칙의 예외다.** Flyway Community에 undo가 없기도 하지만, 있더라도 이미 삭제된 데이터는 되돌아오지 않으므로 본질적인 한계다. 이 비대칭을 감추지 않고 명시한다.

대신 **파괴적 변경을 두 단계로 나눈다**(expand/contract).

1. 먼저 코드가 그 컬럼을 안 쓰게 하고 배포
2. 다음 마이그레이션에서 컬럼 삭제

그러면 1번 상태로 되돌리는 것이 언제나 가능하다. 되돌릴 가능성이 실재하는 이음매 전환 작업에 정확히 맞는다.

### 마이그레이션이 마일스톤의 리듬을 갖는다

`V1`에 전체 스키마를 넣으면 **아직 코드로 써본 적 없는 테이블까지 1주차에 못 박게 된다.** [도메인 모델 확정]이 설계한 것은 맞지만 검증된 것은 아니다.

주차마다 필요한 것만 넣으면 세로로 얇게 뚫는 각 주차가 마이그레이션 하나에 대응하고, 나중에 이력을 보면 **프로젝트가 어떻게 자랐는지가 그대로 읽힌다.** `V1` 사용자·인증(1~2주차), `V2` 콘텐츠·태그·워터마크·묘비(3주차) 하는 식이다.

### 규약에서 도출된 것 (결정이 아님)

- 의존성은 `flyway-core` + **`flyway-database-postgresql`** — Flyway 10부터 PostgreSQL 지원이 별도 아티팩트로 분리됐다
- 위치는 `src/main/resources/db/migration`, 네이밍은 `V<n>__<설명>.sql`
- baseline 설정 불필요 — 새 프로젝트다
- **인스턴스 2대가 동시에 떠도 Flyway가 DB 잠금으로 직렬화**한다. [어드민 계정 초기화 규칙] Q3 같은 경합 처리를 따로 쓸 필요가 없다
- [AWS 배포 형상 확정]의 스냅샷에 `flyway_schema_history`가 함께 담기므로 복원 후 정합성이 유지된다. `ddl-auto`였다면 복원된 스키마와 엔티티가 어긋나도 알 방법이 없었을 것이므로, **이 형상과는 Flyway가 더 잘 맞는다**

### 이 티켓이 드러낸 것 — 삭제 정책 충돌

마이그레이션에 `deleted_at` 컬럼을 넣을지 정하려다 **`CLAUDE.md`와 [도메인 모델 확정]이 어긋난다는 것**이 드러났다. `CLAUDE.md`는 모든 엔티티에 `deletedAt` 소프트딜리트를 요구했고, [도메인 모델 확정] Q6은 물리 삭제로 정했다.

**지도 쪽으로 정리했다.** 관계 테이블에 소프트 삭제를 쓰면 unique 제약과 정면으로 부딪친다 — 언팔로우 후 재팔로우가 `follows(follower_id, followee_id)` 제약에 걸린다. 사용자가 `CLAUDE.md`에서 해당 규칙 두 곳을 제거했다.

[도메인 모델 확정]이 남긴 **"콘텐츠만 예외 검토"** 는 그대로 열려 있다. `deletedAt`이 완전히 사라지는 것이 아니라 필요한 곳에만 남는다.

### 다른 티켓에 미치는 영향

- **[어드민 계정 초기화 규칙]** — Q4의 근거 ②가 무효가 된다. **결정 자체는 유지**된다. 보충을 단다.
- **[12주 마일스톤 구획]** — 1주차에 Flyway 배선과 `V1` 작성이 추가된다. 보충을 단다.

### 결정 주체

Q1~Q5는 에이전트가 추천하고 사용자가 일괄 승인했다("다섯 다 추천대로 가자"). Q6도 추천대로 승인했다. 삭제 정책 충돌은 사용자가 "언팔하면 row가 삭제되는 게 맞지"로 확인하고 `CLAUDE.md`를 직접 수정했다.
